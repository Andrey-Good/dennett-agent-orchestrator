# Dennett — правила реализации

## С чего начать

Репозиторий перезапущен **с нуля без кода**. Бизнес-логика, архитектура и план `D0–D9` утверждены. После команды владельца выполняй текущий этап до его точки приёмки, не подменяя реализацию общими планами.

Опирайся на [статус](docs/implementation/STATUS.md), [план D0–D9](docs/implementation/04_MILESTONE_DEPENDENCY_MAP.md), [процесс](docs/implementation/01_AGENT_EXECUTION_PROTOCOL.md), [тестирование](docs/testing/TEST_CATALOGUE_AND_QUALITY_GATES.md) и профильные разделы спецификаций `00–70` / архитектуры `80–83` (приоритеты источников — в [docs/restart/README.md](docs/restart/README.md)). Не перечитывай весь архив перед локальной правкой.

## Архитектурные и продуктовые границы

- Не восстанавливай старые серверные исходники, тесты, схемы и генераторы из Git без разрешения. **Исключение (решение владельца от 2026-11-23):** визуальный фронтенд десктопного клиента (`apps/desktop/src/App.tsx`, `styles.css`, иконки, полупрозрачные меню и геометрия панелей из `origin/archive/before-code-reset-2026-09-27`) берётся за визуальный эталон один-в-один поверх нового бэкенда (`HeadClient` → `dennett-head`), без переноса старой доменной логики. Сторонние библиотеки разрешены.
- `memoryd` — самостоятельный процесс без зависимости от `Head`; `Head` не встраивает `Memory Core`. PostgreSQL — серверная база; локальная SQLite не является её второй реализацией.
- Агент Dennett не равен модели. Готовый harness исполняет свои инструменты, Dennett — свои. Не вводи собственный универсальный цикл мышления, граф смысловых связей и анкеты делегирования. CLI/MCP/UI ходят через одну прикладную реализацию и не обходят права, память и состояние агента; графика сохраняет пути контракта L.
- Первый продуктовый runtime — **Google Antigravity (`agy acp`)** по [контракту M](docs/specifications/contracts/M_Runtime_Rollout_Contract.md) и приёмке [A01–A12](docs/testing/ANTIGRAVITY_RUNTIME_ACCEPTANCE.md) с двумя разведёнными профилями: интерактивный **Google AI Ultra** (`oauth-personal`) и фоновый **Gemini API key** (`gemini-api-key`). **Claude Code (`R-CLAUDE`)** и **Codex (`R-CODEX`)** отложены за пределы `D0–D9` — не добавляй их зависимости и кнопки входа, и при сбое доступа не переключайся молча на другой движок или платный API.
- Проектируй интерфейс как цельный топовый продукт: без бюрократических форм, ручного ввода путей/заголовков, системных `<select>` и захардкоженных списков моделей (модели и уровни размышления всегда запрашиваются динамически у живого runtime). Базовые ежедневные удобства закладывай сразу по здравому смыслу (владелец не обязан помнить разбивку деталей по `D0–D9`), а идеи на вырост фиксируй в [UX_AND_PRODUCT_BACKLOG.md](docs/design/UX_AND_PRODUCT_BACKLOG.md). **Запрет тихой обрезки:** не выкидывай и не подменяй элементы эталона или спецификации ради удобства текущей схемы БД — делай миграцию либо явно спроси владельца.

## Базовый алгоритм работы с агентами

Это ориентир по умолчанию для многосоставных задач — упрощай его для локальных правок, где рой избыточен, и адаптируй по ситуации:

1. **Продумывание и дельта контрактов (`Claude Opus` / `Carbon`):** для нетривиального UX, логики фичи или развилок проводи короткий мозговой штурм (`claude-opus-4-6-thinking` и/или `gemini-4-carbon-high`), критически сверяя идеи со спеками Dennett и визуальным эталоном. Если список задач или багов уже конкретен, не переписывай его в длинный документ — фиксируй только новые контракты, миграции и спорные места.
2. **Реализация по модулям (`Neon`):** весь код пишет **Neon (`gemini-4-neon-xhigh`)**. Общие контракты, миграции и тесно связанный код внутри одного сервиса делает один автор последовательно. Как только тонкий контракт зафиксирован, независимые контуры (бэкенд, фронтенд, отдельные адаптеры, раннер/CI) запускай параллельно в отдельных копиях (`workspace: "share"` со своими `CARGO_TARGET_DIR`, БД и портами). Держи кусок соразмерным (~1 связный модуль на воркера без раздувания сессии на 200+ ходов, но и без дробления одного файла на микро-агентов): правки по следам ревью быстро закрывает тот же автор на горячем контексте, а на следующий крупный блок бери свежего воркера. Полный прогон тестов и сборку перед сдачей выполняет автор кода.
3. **Проверка по первоисточнику (`Carbon` + `Claude Opus`, без холостых пересборок):**
   - **Живой UI/UX-ревьюер (`Carbon` + встроенный браузер):** обязателен при любых правках интерфейса. Физически открывает живой стек в браузере, прокликивает сценарии глазами требовательного пользователя и сверяет полноту напрямую с эталонным UI и спекой, а не только с промежуточным планом архитектора.
   - **Независимое ревью кода и фазы (`Claude Opus` / `Carbon`):** свежий агент проверяет diff и соответствие первоисточникам по трём осям — отклонения от архитектуры/спеки, воспроизводимые ошибки/дыры безопасности/гонки и реальный оверинжиниринг (отсекая вкусовщину и надуманные придирки). Ревьюер не гоняет часовые полные пересборки повторно за автором и CI, ограничиваясь чтением кода и при необходимости 1–2 быстрыми точечными тестами/мутациями на самых рискованных инвариантах.

## Качество, остановки и общение

- Сохраняй рабочие регрессии прошлых этапов. Критические инварианты проверяй точечной намеренной поломкой с полным откатом. Не снижай пороги/assertions, не выдавай `skipped`, пустой набор или симуляцию за живую проверку; ошибка должна локализоваться по безопасной диагностике без раскрытия секретов.
- Работай в ветке от актуального `main` без force-push и ослабления защиты веток; тесты и fault injection запускай только в изолированном профиле, не оставляя висящих фоновых процессов и заблокированных бинарников.
- После каждого `D0–D9` останавливайся на `H0–H9` и жди явного принятия владельца. Не дергай владельца по приватным деталям кода — спрашивай (с вариантами и рекомендацией) только при изменении продуктовой/архитектурной границы, прав/приватности, необратимом риске данным, заметном расходе или отсутствии обязательного окружения.
- Держи [STATUS.md](docs/implementation/STATUS.md) актуальным и кратким. Отчитывайся владельцу по-русски и лаконично (~3 коротких абзаца по сути функционала, проверок и ограничений, без простыней по файлам и сырых счётчиков тестов). Проект завершён только после `H9`.
