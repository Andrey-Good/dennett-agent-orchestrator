# Dennett — задача, статус и передача работы

Редакция 2.0 · 2026-09-27. Прежняя обязательная система больших JSON Work Packages/Autonomous Batches заменена этим лёгким порядком. Это процесс разработки, не программная топология агентов Dennett.

## 1. Единица работы

Достаточно связного результата: зачем нужен, ссылки на требования, существенная граница и способ проверки. Добавлять риск/миграцию/приватность только когда они есть. Нельзя требовать повторно заполнить то, что однозначно задано текущим этапом.

Пример: «Сохранить черновик при остановке клиента. Проверить перезапуск, пустой ввод, Unicode, повтор одной команды и потерю подтверждения. Не менять намерение пользователя и не отправлять второй раз».

Задача может находиться в issue/PR или текущем разделе STATUS.md. Источник статуса этапов один — [STATUS.md](STATUS.md). Не создавать независимые таблицы одной и той же готовности. Большая связная задача допустима, если её можно проверить; численный лимит файлов не является смысловой границей.

## 2. Ветки и доказательства

Начать ветку `impl/d0-foundation` либо следующего текущего этапа от актуального main. Один writer владеет связным изменением; параллельные работы разделяют также mutable окружение. Ветка не получает автоматически право слияния или обхода required checks.

Нормальный commit описывает наблюдаемое изменение и причину; PR/запись результата содержит точные команды, результаты и ссылку на проверенную сборку. Не нужно вставлять большой отчёт в каждый commit. Результаты относятся к итоговому SHA, а не прошлой успешной версии.

## 3. Статус и пауза

Этап: не начат → в работе → ожидает владельца → принят. Дополнительно заблокирован при реальном препятствии. «Ожидает владельца» разрешён только после необходимых технических проверок. «Принят» ставится по явному решению владельца с датой, build/commit и областью.

После Hn можно начинать D(n+1), когда принят Hn и отсутствуют новые блокировки. Отзыв о картинке не равен приёмке её исполнения. Не идём дальше по истечении времени и не выдаём роль проверяющего агента за владельца.

## 4. Передача новой сессии

В конце связного шага или при вынужденной остановке сохранить в STATUS: текущую цель, ветку/commit, что действительно работает, необходимые команды, выполненные/падающие/не выполненные проверки, важное решение, блокировку и следующий конкретный шаг. Незакоммиченные изменения описываются; их нельзя уничтожать при восстановлении новой сессии.

Новая сессия сверяет checkout и правила, проверяет фактический baseline и продолжает, а не переписывает всё из-за потери чата. Приватное мышление модели не сохраняется как проектная истина. Модель и её настройки меняемы.

## 5. Завершённость

В [карте покрытия](../testing/REQUIREMENTS_COVERAGE.md) каждое обязательное поведение получает проверку и статус. D0 назначает этап всем нормативным семействам, ближайший этап детализирует сценарии. Внезапно обнаруженный пропуск включается в план, а не исчезает из требований.

На H9 нет обязательного сценария без результата. Необязательная технология может отсутствовать; обязательная возможность — нет. Явное изменение согласованного объёма владелец принимает отдельно. Старые каталоги тестов и закрытые WP в истории не засчитываются новой реализации.
