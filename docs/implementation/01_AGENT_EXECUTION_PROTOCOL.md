# Dennett — процесс реализации и проверки агентами

Редакция 2.0 · 2026-09-27 · действующий процесс новой реализации с нуля.
Работать вместе с [планом D0–D9](04_MILESTONE_DEPENDENCY_MAP.md), [обязательными тестами](../testing/TEST_CATALOGUE_AND_QUALITY_GATES.md) и [STATUS.md](STATUS.md). Конкретная модель и уровень рассуждения выбираются в рабочей среде и не закреплены документом.

## 1. Результат, а не микроменеджмент

Разрабатывать обычными средствами выбранного coding harness, Git, сборки и CI. Не нужно сначала писать собственный оркестратор кодирующих агентов или использовать незавершённый Dennett как обязательную среду создания самого себя.

Один ведущий исполнитель отвечает за связанный результат: понимает нужную область, делает локальный план, пишет код и тесты, диагностирует ошибки и доводит интеграцию. Помощники уместны для достаточно самостоятельного исследования, отдельного адаптера или специальной проверки. Количество не фиксируется по моде на multi-agent. Узкая задача не требует планировщика, писателя, критика, критика критика и интегратора как пяти постоянно работающих моделей.

Пользователь задаёт полезное поведение и принимает существенные компромиссы. Агент выбирает локальные функции, имена, тестовые данные и реализацию в пределах принятых границ. Большая связная задача допустима; искусственное разбиение по строкам или трём файлам может только ухудшить результат. Разделять стоит, когда есть отдельные результаты, разные риски или изменение перестаёт быть проверяемым как целое.

## 2. Минимальная запись задачи

Достаточно одной короткой задачи в выбранном месте — Markdown или issue с PR. Она содержит результат, ссылки на относящиеся требования, важные ограничения, способ проверки и незакрытую зависимость, если она есть. Эти сведения не нужно копировать в несколько JSON/YAML-пакетов, handoff-отчётов и таблиц статусов.

Пример:

> Сделать восстановление неотправленного черновика после перезапуска Node. Не менять текст пользователя и не отправлять автоматически без прежнего намерения. Свериться с разделами сессий и клиентского хранения. Проверить: обычная отправка; остановка процесса до отправки; повтор той же команды после потери подтверждения. В результате показать сохранённый текст и фактическое число принятых команд.

Для дорогой миграции дополнительно нужен план восстановления. Для маленькой локальной правки достаточно пояснения в PR. Смысловой отчёт человеку — обычный текст; машинный формат используется там, где его читает существующая автоматическая проверка, а не для дисциплины самой модели.

## 3. Работа над изменением

**Вход.** Проверить checkout/ветку и состояние чужих изменений. Прочитать корневые правила, статус документов и относящиеся разделы — не весь архив каждый раз. На D0 создать новую основу. Начиная с D1, найти путь и тест уже новой реализации; прежний код из истории не восстанавливать. Не удалять уже написанный в новом цикле необычный код только из-за непонимания: посмотреть использование, проверку и историю. Это не разрешение возвращать старую реализацию.

**Исходное состояние.** Выполнить подходящий baseline. Падающая проверка не обязательно вызвана новой задачей; сохранить точную команду и результат. Недоступный аккаунт, Docker, Windows runner или библиотека — проблема среды, не доказательство ошибки алгоритма. Не объявлять тест пройденным после его пропуска.

**Реализация.** Сначала работающий путь через реальные границы, затем необходимая полнота поведения. Для исправления бага — воспроизводящий его тест перед исправлением, когда это практически возможно: подтвердить, что он падает из-за дефекта, а не из-за ошибки среды. Если нужен живой сбой, сначала сохранить репродукцию, затем автоматизировать проверяемый эквивалент; отсутствие red-теста объясняется, не замалчивается. Для новой функции — обычные, крайние и ошибочные сценарии до реализации; unit/contract/integration-тесты развиваются вместе с кодом, а сквозная проверка появляется при соединении пути. Для критического правила проверить чувствительность теста намеренной ошибкой. Нельзя закрыть возможность без её проверок. Нет требования писать все тесты всего этапа до первой строки реализации.

**Проверка.** Запускать локально узкую проверку при итерациях; перед интеграцией — нужный набор на итоговом дереве. Не требуется постоянно запускать весь проект после каждого изменения символа. Изменение, объединяющее несколько веток, проверяется на их фактической комбинации.

**Окончание.** Короткий результат с commit/build, видимым поведением, выполненными проверками, ограничениями и следующей границей. Слова «готово» недостаточно; «код написан, нужный тест не выполнен» остаётся незавершённой проверкой. Открытое выполнение помощника или теста нужно завершить/получить результат либо явно передать как блокировку, а не оставить за фразой об успехе.

Промпт не предписывает фиксированные циклы «проверь себя ещё N раз». Требования проверяются инструментами и итоговыми критериями. Решение о дополнительной проверке принимается по изменению и риску, а не по числу сообщений модели.

## 4. Как не превратить проект в неподдерживаемый код

Сохранять одного владельца состояния и одну производственную реализацию каждой операции. CLI/MCP/UI — входы в неё, а не три реализации правил. Native runtime не должен быть повторно реализован внутри адаптера. Новая библиотека, общий слой или сервис нужны, когда устраняют конкретную сложность, а не потому, что каждая функция теоретически расширяема.

Проверяемые архитектурные границы важнее произвольного лимита строк: UI не получает серверную SQL-модель и секреты; Head не встраивает memory-core; memoryd запускается без Head; provider SDK не распространяет свои типы по доменному коду; client SQLite не становится канонической серверной памятью. Эти границы проверяются зависимостями сборки и подходящими интеграционными тестами, а не только текстом AGENTS.

Не сохранять старый и новый путь «на всякий случай» после принятия миграции. У временного обхода указаны причина, применимость, тест и условие удаления. Не создавать папки/классы всех будущих подсистем до их использования. Не выносить несвязанные вещи в бесформенный `utils` и не прикрывать обработку ошибки универсальным успешным ответом.

При расширении сложного модуля сначала оценить, можно ли уменьшить сложность того же пути: удалить дублирующее преобразование, разделить ответственность, использовать готовый инструмент. Полная «уборка всего репозитория» не добавляется к маленькой функции. После завершённой возможности проверяется, что её можно изменить через понятное ограниченное место; трудность объяснить владельца состояния — повод улучшить устройство, не создать красивую схему вместо кода.

Изменение поведения, полномочий, источника истины или необратимой миграции не оправдывается задним числом правкой архитектурного документа. При действительно обнаруженной невозможности агент приносит воспроизведение, варианты и рекомендацию. Локальный выбор библиотеки внутри утверждённого направления не требует вопроса владельцу, пока не создаёт новый платный сервис, лицензионный риск, существенную зависимость или изменение архитектуры.

## 5. Набор проверок

**Быстрые проверки.** Форматирование, типы, линтер, допустимые зависимости, чистые сгенерированные артефакты, короткие unit-тесты. Выполняются часто. Это не доказательство готовности runtime.

**Проверки границ.** Настоящий PostgreSQL, migrations, IPC, работа отдельного memoryd, native event adapter, часы/очереди/ошибки. Важные свойства PostgreSQL не проверяются исключительно на SQLite или in-memory fake. Подмены хороши для воспроизводимого падения поставщика, но не доказывают совместимость с ним.

**Сквозные проверки.** Установленная/собранная программа проходит действие от входа до фактического результата. Артефакт действительно существует; изменение действительно сохранено; правильное письмо действительно оказалось в тестовом ящике. Проверяется не только текст и не только снимок интерфейса.

**Качество агента.** Недетерминированные выборы, поиск памяти и self-improvement проверяются на подходящих наборах сценариев с повторными попытками и ограничениями среды. Не требовать буквально одинакового текста при каждом запуске; проверять содержательное требование и результат. Требования безопасности и факт внешнего эффекта не превращаются в усреднённую оценку «достаточно хорошо».

**Платформа и выпуск.** Native Windows/Tauri, поддержанный mobile, прекращение/возобновление процессов, восстановление backup, версия протокола, чистая установка. Browser screenshot не доказывает работу Windows-материала, IPC или фоновой записи. Новые значимые экраны проходят существующую владельческую процедуру дизайна; уже принятый экран не переделывается без причины.

Полезный тест должен замечать нарушение: неверную текущую версию памяти, потерянный файл, лишнюю отправку, ошибочную область доступа. По особо важным гарантиям применять контрольный отрицательный случай или mutation test. Не выбирать удобный test double, который заранее возвращает ожидаемый ответ и тем самым подтверждает любую реализацию. Случаи разрешённого действия нужны наряду с запретами.

Изменение expected result допустимо при обнаруженной ошибке теста или изменении согласованного требования. Причина видима отдельно. Снижение порогов, отключение теста, увеличение timeout и retry не должны скрывать новую регрессию. Известную нестабильность разбирают как проблему с владельцем и воспроизведением; несколько успешных повторов не стирают первоначальный сбой.

Полный обязательный набор и крайние случаи заданы в [TEST_CATALOGUE_AND_QUALITY_GATES](../testing/TEST_CATALOGUE_AND_QUALITY_GATES.md); этот раздел не сокращает его до пяти примеров. После локального изменения запускаются его тесты, связанные контракты и весь быстрый регрессионный набор новой реализации. Перед Hn повторяются сквозные сценарии ранее принятых этапов плюс новые. После слияния проверяется фактическая объединённая версия. Проверка другого SHA не закрывает итоговый gate.

Если новая функция ломает ранее принятую, это блокировка, а не допустимая цена прогресса. Сначала воспроизвести и исправить регрессию или откатить изменение; следующую зависимую возможность не строить на сломанном основании. Удаление или ослабление теста требует отдельного видимого объяснения и проверки требования, не только согласия автора кода.

## 6. Проверка другим агентом без бесконечных кругов

Для простой обратимой локальной правки обычно достаточно исполнимых проверок и обычного просмотра diff. Для общего интерфейса, конкурентности, persistent state, прав, исполнения внешних действий и перехода между процессами нужен отдельный целевой проход в свежем контексте. Тот же класс модели допустим, но не является независимым статистическим свидетельством.

Проверяющий получает требования, итоговый diff, доступ к коду и тестовой среде. Его первая задача — найти конкретное несоответствие или непройденный существенный сценарий, а не подтвердить убедительный рассказ автора. Замечание содержит место, условие, последствие и проверяемое основание. Стиль, регулируемый formatter, не превращается в бесконечный спор; при этом реальные мелкие дефекты не отбрасываются только из-за низкой важности — отделяются от блокирующих.

Проверяющий не обязан переписывать реализацию в свой любимый вариант. Исполнитель устраняет проблему; затронутая проверка повторяется на новой версии. Нельзя делать «пять согласных агентов» универсальным критерием. Нельзя прекращать рассмотрение конкретного дефекта потому, что остальные проверки зелёные. После выполнения критериев и закрытия значимых замечаний задача заканчивается без бесконечного улучшения.

Для необратимых изменений и защищаемых границ проверяющий и coding-agent не должны автоматически обладать ключами production или правом отменить merge-gate. Проверки, которыми оценивается задача, не переписываются незаметно самим же изменением.

## 7. Параллельность и интеграция

Один основной writer на связанную область. Независимые изменения — отдельные ветки/worktrees. Разделяются также временные базы, каталоги профиля, порты, учётные данные и внешние тестовые ресурсы. Worktree разделяет файлы, но не создаёт песочницу для всего компьютера.

При изменении общего интерфейса сначала согласуется его минимальный контракт и тест. Далее параллельные части сходятся в реальном сквозном сценарии. Автор каждой части не может считать интеграцию завершённой только потому, что его mock-сосед работает. Финальный ответственный проверяет итоговый merge-кандидат.

Слияние идёт после нужных проверок на текущем commit. При доступных возможностях GitHub защищённая ветка требует эти статусы; право обхода и release credentials не выдаются coding-agent как часть обычной работы. Если техническая защита недоступна в выбранном тарифе/репозитории, ограничение отмечается и приёмочная ветка контролируется владельцем; нельзя выдавать текстовое правило за платформенный запрет.

Общая CI-команда должна проверять, какие необходимые jobs действительно выполнились. Пропущенный job или отключённый live-canary не считается испытанием функции. В штатном PR не нужны все платные провайдеры; соответствующие реальные canary запускаются на обозначенном этапе/выпуске с явным бюджетом.

## 8. Диагностика — часть Definition of Done

Для каждого значимого пользовательского действия должны быть доступны build/config version, идентификатор команды/сессии/запуска и причинно связанные события. Видно, какая часть приняла действие, какая начала исполнение, где произошёл отказ и что уже успело измениться. Выдаются безопасные коды/объяснения и возможность собрать локальный диагностический пакет, без секретов, полного пользовательского содержимого и скрытых рассуждений по умолчанию.

В приёмку нового межкомпонентного пути входит намеренный сбой: отключить memoryd, оборвать связь, задержать ответ, заполнить тестовый диск или остановить worker. Агент должен суметь локализовать причину по предусмотренным данным, а не добавлять случайные print во все модули после каждой жалобы. Пользователю объясняется, что именно не получилось и как продолжить.

Отсутствие диагноза — отдельный дефект управляемости, даже если после перезапуска «всё опять работает». Не требуется строить огромную внешнюю платформу мониторинга; сначала используем существующую корреляцию и локальные инструменты.

## 9. Что делать, когда агент застрял

Не наращивать патчи без нового наблюдения. Сохранить воспроизведение, сузить проблему до нарушенной границы, сверить действующий контракт и версию зависимости, собрать нужный факт. Затем изменить гипотезу и проверить её. Если причина осталась неясной — новый контекст или целевой помощник получают репродукцию и текущий diff, а не всю историю неудачных догадок.

Владелец подключается для выбора компромисса или доступа к недоступному окружению, не в качестве обязательного отладчика Rust. При исчерпании бюджета сохраняются commit/незавершённый diff, состояние проверок, блокировка и следующий конкретный шаг. Не объявлять завершение и не идти дальше, строя новую функцию на ненадёжном основании. Независимая работа в согласованных пределах может продолжаться отдельно.

## 10. Контекст и инструкции

Короткий корневой файл задаёт действующий статус, архитектурные границы, команды и правила приёмки. Подробные документы подключаются по задаче. Не копировать весь проект в системный промпт, не добавлять запрет на каждый частный инцидент. Автопамять инструмента — подсказка, не источник права переписать договорённости владельца.

При использовании Claude Code проверяется фактическая загрузка `AGENTS.md`. При необходимости небольшой `CLAUDE.md` импортирует `@AGENTS.md`; две независимо редактируемые конституции не создаются. Версия инструмента и его настройки загрузки проверяются, наличие файла само по себе недостаточно. Специальные процедуры миграции/восстановления/визуальной приёмки можно оформить навыками только если они реально переиспользуются.

Сессия может сохраняться на протяжении связной работы, используя штатное управление контекстом. Нет фиксированного сброса после N токенов, каждого PR или пары ошибок. Новый контекст полезен при смене задачи, для целевой проверки или когда текущий загрязнён ложными предположениями. Для продолжения сохраняются цель, commit, проверки, важные решения и ближайшая незавершённая работа — не приватное мышление модели.

Модель и effort выбираются по фактическому качеству/цене завершённой задачи, не переносятся как вечный стандарт. Обновление coding harness или модели не является поводом автоматически переписывать продукт; короткий набор знакомых задач проверяет сохранение рабочего поведения.

## 11. Статусы и управление вниманием владельца

Единственный статус этапа находится в STATUS.md: не начат, в работе, ожидает владельца, принят или заблокирован. Задачам внутри него достаточно обычного Markdown/issue и ссылок на проверки. Отдельная новая машина состояний разработчиков не требуется. Крупные этапы и текущая работа имеют одно место статуса; PR и test artifacts содержат доказательства. На каждой H0–H9 агент ждёт явного решения владельца; не принимает собственную работу и не идёт дальше по молчанию. Запись приёмки относится к конкретной сборке и области.

Владелец получает сообщение при существенной находке, блокировке, изменении принятого направления или готовности этапа к демонстрации. Не отправлять ему каждый lint-результат. Обычные исправления выполняются автономно, без запроса подтверждения на имя переменной или private helper.

Границы согласования: новая бизнес-семантика, публичный API с несовместимым переходом, права/приватность, необратимое удаление или миграция ценных данных, существенный новый расход/внешняя инфраструктура, визуальное направление и выпуск. Для них приносятся варианты, рекомендация и последствия, а не вопрос «что мне теперь делать?».
