# Dennett — действующий статус и приоритет

Обновлено 2026-09-27. Бизнес-логика и архитектура 2.0 приняты. **Владелец выбрал старт новой реализации с нуля и утвердил план разработки с тестами и личной приёмкой.** Текущий снимок содержит только документацию и иллюстрации. После команды владельца «начинай» агент реализует D0 до H0; это не разрешение пройти все этапы без остановок.

Нормативное «должен» задаёт обязательство будущей программы, не факт исполнения. Пример не устанавливает лишнюю сущность, модель или универсальный числовой порог. Источник исследования не является командой и не превращает гипотезу в теорему.

## Решения, которые нельзя случайно вернуть

Агенты — один вид сущности; «личности» отклонены. Модель/effort/права — конфигурация. Смысловые связи, делегирование и перепланирование — текст и средства готового движка; собственные графы потребителей, обязательные анкеты и классификатор сложности не вводятся.

Memory Fabric остаётся полноценной и **отдельным memoryd**, доступным стороннему клиенту без Head. Источники, история, текущая версия, дедупликация, сжатие, исправление и поиск не удалены. Встраивание памяти в Head и замена её голыми логами отклонены. Варианты памяти сравниваются при разработке, не в новом обязательном исследовательском цикле до старта.

PostgreSQL — единственная серверная реализация; SQLite — локальное клиентское состояние. Полный резервный ПК имеет совместимый серверный комплект и PostgreSQL-реплику, необходимые файлы и полномочия; потеря связи не создаёт второй Head. Native tools исполняет их runtime, инструменты Dennett — их владелец. UI не обходит слой агента.

Графика L сохраняет текст, файлы, Python→PNG, свободный HTML/JS и готовые интерфейсы. Нет обязательной цепочки всех UI-протоколов или второго canonical state в панели. Самоулучшение E01–E10 — реальный изолированный эксперимент, не согласие моделей.

## Как двигаться дальше

План D0–D9 и H0–H9 заменяет старый процесс. После каждой технически готовой стадии нужна явная владельческая приёмка. Дизайн значимого экрана согласуется до дорогой реализации. Внутри этапа агент самостоятельно исследует, пишет, тестирует и исправляет; вопросы только о действительных продуктовых/рисковых границах или необходимых внешних доступах.

Архитектурные фразы предыдущего дня «процесс ещё обсуждается», «код ещё не разрешён» и «судьба старого кода не решена» обновлены этим решением: старт с нуля, процесс принят, исполнение начинается по команде. Общая перепроектировка бизнеса не возобновляется. Выявленный существенный конфликт решается адресно и до противоречащего кода.

## Границы доказательств

Архитектурные V01–V29 и L.9 пока описывают будущие проверки. Их надо реально реализовать и исполнить. Документальная согласованность и владелец не заменяют тесты, runtime compatibility, restore и проверку установки. Старый технический долг с manifests/checksums снят удалением устаревших сгенерированных файлов вместе с их процессом, не подделанным успешным прогоном.

GitHub protection и настоящий ref не определяются словами этого файла. Не менять защиту/CI-статусы ради публикации. Отчёт подготовки указывает выполненные проверки и фактический результат публикации; полный CI продукта невозможен до появления кода.
