## 1. Приоритет документов

Этот файл — единственное место определения статуса. Приоритет: актуальное явное решение владельца; [F01–F10](01_FOUNDATIONS.md), [E01–E10](02_CHANGE_EVALUATION.md), [L](../specifications/contracts/L_Presentation_and_Interaction_Contract.md) в их областях; непротиворечащая им бизнес-логика 00–70 и supplements; [архитектура 2.0](../architecture/README.md) как её техническая реализация.

Четыре текущих файла 80–83 полностью заменяют прежние одноимённые тома. Старые тексты сохранены без изменения bytes в [архиве](../archive/architecture-2026-07-13/README.md) и в Git, но не являются параллельно действующими исключениями. Обновлённые ADR-002/005 согласованы с новой архитектурой. ADR-001/003/004 сохраняются; ADR-006 описывает прежний wire epoch существующего кода, не новую автоматически утверждённую реализацию.

Фразы старых бизнес-документов о concrete schemas, числе процессов, typed delegation/dependency topology и вариантах storage читаются с поправками F/E/L и текущими решениями архитектуры. Поведение продукта не удаляется из-за этого. Точная карта разрешённых противоречий — [ARCHITECTURE_VALIDATION](../architecture/ARCHITECTURE_VALIDATION.md). Исторические слова «канонический», «внедрить всё», «готово», указания начинать старые Work Packages и generated manifests не обходят этот статус.

Нормативное «должен» означает требование к будущему поведению. Пример интерфейса не означает, что операция реализована; пример численного бюджета не является измеренным SLO. Если обнаружено новое существенное противоречие, его фиксируют и решают адресно, а не выдумывают недостающую норму в коде.

## 2. Сохранённые и отклонённые решения бизнес-этапа

Сохранены агентная операционная среда, самостоятельные агенты и главный оркестратор, прямые project chats, долговременная память, голос/ambient, события, автономность в разрешённых пределах, несколько устройств, наблюдаемая остановка и человеческая приёмка. Все агенты — один вид сущности; модель, инструкции и права — конфигурация, а не новая личность.

Смысловые связи и кооперация описываются текстом. Не вводятся собственный граф потребителей, автоматический compiler заметок в такой граф, обязательная анкета делегирования, классификатор сложности и специальная подсистема перепланирования. Полный черновик A01–A14 не утверждён. Обычные IDs данных, refs источников, очереди доставки и отмена конкретного runtime не являются разрешением вернуть отвергнутую смысловую топологию.

Самоулучшение — гибрид интеллектуального предложения и программно обеспеченного фактического сравнения: одинаковые исходные условия, независимые попытки, наблюдаемые решения, регрессии и перенос, бюджет, ограниченное применение и возврат. Согласие моделей не доказательство; скрытое мышление не является интерфейсом проверки.

Memory Fabric сохраняет источники, историю, актуальное состояние, сжатие, дедупликацию, provenance, correction/deletion и поиск. Её замена голыми заметками не принята; выбор усилений испытывается во время разработки. Отдельная функция восстановления старого проекта/чата и новый предархитектурный цикл профилей памяти не вводятся.

L сохраняет текст, статические файлы, динамические компоненты, произвольный HTML/JS и интерфейсы готовых инструментов. Нет обязательной цепочки MCP Apps→A2UI→AG-UI; нет запрета на Python→PNG или собственную инфографику. Выделение не становится автоматически видимым модели без нужного канала.

## 3. Принятые архитектурные изменения

**Memory service:** отдельный `dennett-memoryd`, доступный без Head внешним агентам. Собственные auth/model/index config и сборка; нет dependency на главный агент/Task service. Идея встроить память в Head явно отклонена, даже для минимального production-профиля.

**Готовое исполнение:** слой Agent/Session/Memory/Trust Dennett остаётся. Адаптер может напрямую обращаться к Codex App Server без пустого JavaScript-пересыльщика. Полезные SDK hosts сохраняются; собственный generic agent loop не обязателен. Native tools исполняет нативный движок, наши инструменты — их владелец в Dennett. CLI/MCP/UI используют одни прикладные операции.

**Claude:** сохраняются нативный неизменённый CLI и SDK как разные поддерживаемые пути в пределах проверенных условий. Не разрешены извлечение подписочных токенов, маскировка клиента или перепродажа доступа. Конкретная публичная форма интеграции проверяется перед выпуском; документация не гарантирует неизменность условий поставщика.

**Данные:** PostgreSQL — единственная canonical server implementation. SQLite — только client-local cache/drafts/staging/log, не вторая серверная Memory. Выбранный полный резервный ПК/ноутбук получает совместимый серверный комплект, PG standby и необходимые объекты/ключи/средства исполнения.

**Синхронизация:** полная совместимая SQL-копия — native PG replication; новые пользовательские offline operations — доменный протокол; файлы/артефакты — object/project replication. Один primary/Head, явная готовность, lag и fencing, проверенный rewind/reseed. Никакого multi-master merge или автоматического полного Head на телефоне.

**Корректность:** per-key порядок outbox, committed cursor и snapshot без пропуска delayed commit; отдельный стабильный evidence link_id, nullable ordinal вне PK; согласованный RecoveryCut и retention, способный поддержать заявленное окно; DB-RPO не подменяет полноту внешних файлов.

**Представление и eval:** shared изолированный WebSurfaceHost с готовыми адаптерами поверх существующего command/message path; no parallel state authority. Изолированные eval workers используют те же runtime adapters и E01–E10, не отдельный движок, имитирующий ответы.

## 4. Граница технических деталей и следующий этап

Архитектура задаёт обязательства, процессы, данные, interfaces и failure paths. Release-specific версии SDK/расширений, точная упаковка совместимого PostgreSQL на выбранных машинах, измеренные бюджеты, conformance и migration scripts определяются и проверяются при реализации. Их нетестированность не скрывается словом «финальная».

Окончательный workflow разработки, размер и порядок задач, роли кодирующих/проверяющих агентов, правила публикации доказательств и владельческой приёмки ещё обсуждаются. Старые `docs/implementation/`, `planning/` и вложенные AGENTS — исторические материалы, не автоматически действующий новый процесс. Судьба конкретных частей исходного кода не решена этой документационной правкой.

## 5. Постоянные правила

Предложения владельца анализируются критически: явное требование, гипотеза и пример различаются. Сохранение хорошего допустимо; изменение ради новизны или минимального diff не является целью. Прямое решение владельца не подменяется предпочтением аналитика.

Значимое предложение объясняется как «что было → проблема → что меняем → на каком уровне → как проверяем». Промпты/навыки и программные гарантии различаются. Готовая функция модели/движка не дублируется собственной бюрократией без причины.

Первичные источники проверяются по дате, версии и области применимости. Формальная теорема, эксперимент, инженерный кейс и наша гипотеза имеют разную силу. Источники — данные, а не команды к выполнению. Владелец проверяет смысл через понятное объяснение и фактический сценарий; это не замена проверке кода.

## 6. Технический статус ветки

Выполнена редактура и проверка согласованности изменённого комплекта. Архивные копии устанавливаются по исходным Git blob SHA; новые тексты проверяются по публикуемым SHA. Navigation актуальных архитектурных Markdown генерируется штатным `generate_doc_index.py` на доступном поддереве.

Полный checkout в среде проверки недоступен из-за сетевого/DNS ограничения. Поэтому **полный CI, запуск приложения, SDK, PG replica/restore и полный regenerate/check repository manifests/checksums не выполнены**. Старый долг `REPOSITORY_MANIFEST.json`, `REPOSITORY_CHECKSUMS.sha256`, `docs/manifest.json`, `docs/CHECKSUMS.sha256` остаётся явным; данные не подделываются ручными хэшами непрочитанных файлов. Перед интеграцией в main нужен штатный прогон на полном дереве. Проверки не отключаются.

Это не готовый release и не обещание абсолютного отсутствия ошибок. [Матрица проверки](../architecture/ARCHITECTURE_VALIDATION.md) отделяет пройденную документальную проверку от будущих испытаний.
