# Источники процесса разработки и тестирования

Проверено 27 сентября 2026 года. Первичные страницы прочитаны при подготовке финального процесса. Это инженерные рекомендации и документация, не доказательство безошибочной автономной разработки. Модель-исполнитель и её версия не закрепляются. Доступность конкретных CLI-команд/режимов проверяется в установленной версии при D0.

<a id="t01"></a>

## T01. Проверяемый результат и достаточный контекст

[Claude Code — Best practices](https://code.claude.com/docs/en/best-practices).

Проверены разделы проверки работы, plan/code, коротких инструкций, CLI, параллельных сессий и review. Поддерживает исполнимый критерий вместо уверенного отчёта и чтение относящегося к задаче материала. Не требует постоянной команды помощников, плана для каждой мелочи или прав на production. В Dennett: один связный исполнитель, тесты/сборка/демонстрация, целевой review по риску. Ни hook, ни подсказка модели не заменяют защищённый merge-gate.

<a id="t02"></a>

## T02. Общие инструкции без дублирования

[Claude Code — Memory](https://code.claude.com/docs/en/memory).

Проверена загрузка проектных инструкций и импорт через @path. CLAUDE.md импортирует AGENTS.md, подробный workflow читается по ссылкам. Наличие файла не доказывает его загрузку в любой версии/настройке. В D0 это проверяется; второй набор независимо редактируемых общих правил не создаётся.

<a id="t03"></a>

## T03. Длительная разработка и цена надстроек

[Anthropic — Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 24 марта 2026 года.

Инженерный эксперимент сравнивает организацию создания и оценки приложений и обсуждает сокращение scaffolding при изменении моделей. Это примеры с конкретными задачами, не универсальные нормы числа агентов и длительности сессии. Используем сохранение результата между сессиями и проверку настоящего приложения; не наследуем сложную orchestration без пользы. Старые обходы слабостей модели могут быть пересмотрены, но обязанность доказать работоспособность сохраняется.

<a id="t04"></a>

## T04. Результат в среде, а не рассказ

[Anthropic — Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

Проверены различие transcript/outcome, испытания, grading и ограничения оценки. Для Dennett надпись «отправлено» не равна факту отправки, а успешная trajectory не гарантируется объяснением модели. Нужны реальные наблюдения и подходящие повторные задачи для недетерминированного качества. Наши E01–E10 и регрессии используют это различие; статья не доказывает достаточность конкретного размера нашего набора.

<a id="t05"></a>

## T05. Зелёный статус может скрывать пропуск

[GitHub — Status checks](https://docs.github.com/en/pull-requests/reference/status-checks) и [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

Проверены skipped/neutral и привязка к актуальному SHA. Поэтому gate новой реализации проверяет фактический запуск нужных jobs и tests, не только внешний зелёный значок. Required check нельзя подделывать из coding-сессии. Техническая защита GitHub настраивается владельцем при необходимости; этот документ не утверждает, что она уже изменилась.

<a id="t06"></a>

## T06. Возврат файлов не отменяет побочные эффекты

[Claude Code — Checkpointing](https://code.claude.com/docs/en/checkpointing).

Проверены границы сохранения изменений. Rewind не является заменой Git, backup PostgreSQL или возврата внешней отправки. Для испытаний используем отдельные данные и проверяемое восстановление. Разрешение агенту исправлять файлы не даёт права удалять рабочую установку или применять migration к ценной БД без соответствующего gate.

<a id="t07"></a>

## T07. Генеративные тесты и контрпримеры

[Proptest — Getting started](https://proptest-rs.github.io/proptest/proptest/getting-started.html) и [исходник документации](https://github.com/proptest-rs/proptest/blob/main/book/src/proptest/getting-started.md).

Документация показывает генерацию входов, shrinking и перенос найденного случая в регрессию. В Dennett это кандидат для проверки свойств, не обязательный backend каждой проверки. Seed и версии помогают воспроизведению; сам минимальный вход/последовательность предпочтительно сохраняется, чтобы будущая смена генератора не потеряла суть дефекта.

<a id="t08"></a>

## T08. Fuzzing входных границ

[Rust Fuzz Book](https://rust-fuzz.github.io/book/) и [cargo-fuzz guide](https://rust-fuzz.github.io/book/cargo-fuzz/guide.html).

Проверены назначение fuzzing, corpus и test-only конфигурации. Используется для parsers/импорта/протоколов, не как доказательство функционального качества. Поддержку платформ, sanitizer и nightly необходимо сверить перед установкой: разные страницы/версии могут различаться. Отключённая ради fuzz проверка не должна попадать в production или подменять полноценную проверку безопасности.

<a id="t09"></a>

## T09. Чувствительность тестов

[cargo-mutants](https://mutants.rs/).

Официальное руководство рассматривает мутационное тестирование как способ обнаружить дефекты, которые обычные тесты пропускают. В Dennett выборочные мутации важных правил применяются в изолированной копии. Это не требование дорогого полного mutation-run на каждый commit и не разрешение оставлять дефектный код в продукте.

## Границы этой подготовки

Прочитаны актуальные источники, текущая архитектурная база и предыдущий проект процесса. Изменён план старта: вместо выборочного сохранения кода — явный greenfield. Созданы правила реального тестирования, regressions, H0–H9 и дизайна. Никакие product tests, benchmarks, live SDK, PG-replication/restore или CI приложения при этой документационной подготовке не запускались.

Старый материал про жёсткие анкеты/модельные пресеты не превращается в новые нормативные требования. Собственные решения процесса — проектный выбор, основанный на согласованных целях и проверяемых границах. При разработке проверяется их полезность; требование реальных доказательств и владельческих решений не заменяется доверчивостью к новой модели.
