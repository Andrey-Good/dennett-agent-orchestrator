# Dennett: клиенты, представление, поставка и проверка

Версия 2.0 · 2026-09-26 · согласованная архитектурная база, не разрешение начать реализацию.
[80](80_Dennett_System_Architecture_and_Runtime_Topology.md), [81](81_Dennett_Data_Memory_Storage_Sync_and_Protocol_Architecture.md) и [82](82_Dennett_Agent_Voice_Capability_and_Integration_Architecture.md) определяют исполняемые и доменные границы. Этот том реализует в архитектуре бизнес-логику desktop/mobile и [контракт L](../specifications/contracts/L_Presentation_and_Interaction_Contract.md). Прежний том заменён целиком; исходные материалы сохранены в [архиве](../archive/architecture-2026-07-13/README.md).

## 1. Клиенты не являются системой исполнения

Desktop: Tauri 2 Rust bridge + React/TypeScript. Mobile: React Native + native Kotlin/Swift component для ОС, local persistence, capture, secure authentication и background tasks. Shared TypeScript используется для доступных presentation types, форматирования и client models, но не дублирует серверные правила grants/effects/Memory.

UI отправляет команды владельцу состояния, показывает accepted/pending отдельно от completed, читает снимки/изменения с revision и freshness. Локальное закрашивание карточки не выдаёт permission и не завершает Run. Доступ к providers идёт через слой агента Dennett, не напрямую из кнопки. Память вызывается через memoryd API, а не встроенную копию Memory Core.

Окно можно закрыть, не завершив серверный runtime. Lifetime постоянных процессов принадлежит штатным механизмам ОС; Tauri sidecar не является единственной гарантией фоновой работы. Mobile не обещает вечное выполнение JS или собственный полный Head только потому, что хранит локальные данные [AR17].

## 2. Desktop и общие команды

Расположение рабочих пространств, menus, search, Inbox/Radar/Library, tabs, split views, Inspector, artifacts и accessibility сохраняется из спецификации 60. Поздние принятые visual-направления WP-M01-003 не заменяются старой самодельной проекцией wallpaper: native material проверяется на Tauri, а намерение дизайна — отдельной визуальной приёмкой. Архитектурная редакция не меняет палитру/макет без запроса владельца.

Frontend разделяет remote canonical cache, local presentation state, uncommitted drafts и local operation queue. TanStack Query или выбранный эквивалент владеет remote cache; transient component state не превращается в копию доменной БД. Большие списки виртуализированы, вывод обновляется порциями, focus/scroll не прыгают при стриминге. Сложные вычисления/индексация не выполняются на UI thread.

Единый command registry связывает кнопку, клавиатуру, голос, меню, CLI/MCP-фасад и видимое действие с прикладной операцией. Context-dependent UI actions могут остаться локальными; consequential commands не обходят владельца. Command descriptor содержит label/context/access requirements, а не полный смысловой план агента.

Optimistic UI допустим для обратимой локальной организации и drafts; не для выдуманного разрешения, подтверждённой отправки, полного удаления, готового backup или финального Run outcome. Отказ возвращает понятное состояние и сохранённый ввод.

## 3. Mobile, offline и системные поверхности

Телефон остаётся быстрым доверенным remote: glance/capture/decide/continue, project/voice chat, уведомления и handoff. Widget/notification/deep link вызывает ту же команду; payload уведомления не является полномочием. Точный recipient/версия/срок проверяются заново. Просроченная карточка отвечает already resolved/superseded, а не выполняется второй раз.

Локальное сохранение текста, capture manifest и operation_id происходит до сообщения пользователю о сохранении. Media сначала надёжно staged; upload/ASR/classification идут позже. Process death восстанавливает drafts и capture journal, но не превращает незавершённое подтверждение в принятое.

SQLite/нативное хранилище используется только для этих местных обязанностей и cache. Полная серверная логика PostgreSQL не портируется в мобильную SQLite. Full-replica ПК из 80 имеет отдельный серверный комплект и не ограничивается мобильной моделью.

Android persistent work/foreground service и iOS разрешённые background mechanisms применяются по типу операции. Микрофон, камера и screen capture запрашивают реальные OS permissions; отказ/потеря audio focus видимы. Upload повторяется безопасно по content/operation identity. При возврате показываются подтверждённые изменения и восстанавливается позиция, не автоматически отправляется старый draft.

Handoff различает перенос view, разговора, media и исполнения. Получение ссылки на телефоне не повышает его до Head. При отсутствии требуемой возможности предлагается доступный просмотр/другое устройство без ложной эквивалентности.

## 4. Единая архитектура представления

Пять путей L остаются равноправными доступными средствами, не ступенями обязательного усложнения:

- Markdown/text и обычные вложения;
- статические PNG/SVG/PDF/audio/video;
- UI из поддержанного каталога компонентов;
- произвольный изолированный HTML/CSS/JS/SVG/Canvas/WebGL;
- интерфейс подключённого инструмента, включая MCP Apps.

Python → изображение → Artifact/viewer не зависит от работоспособности MCP Apps/A2UI. Пользователь может принести свой исходник; отсутствие подходящего компонента не заставляет выпускать новый плагин или переписывать графику под каталог.

**Принимается один повторно используемый механизм Web Surface Host**, а не отдельная платформа на каждый формат. Внутри разные материалы получают отдельные изолированные контексты/каналы. Один механизм не означает общий DOM, origin, credential jar или привилегии.

Обычные просмотрщики и текст не обязаны проходить через этот механизм. Generated web artifact открывается как артефакт с исходником, не требует регистрации собственного MCP-сервера. External MCP App получает протокольный адаптер. Component UI использует готовый совместимый A2UI renderer; специфическая графика может быть соседней свободной surface.

## 5. Готовые UI-компоненты и обмен

### 5.1. MCP Apps

Для обмена с совместимой панелью используется официальный AppBridge/host-side SDK вместо собственной копии протокола [AR16]. Это компонент связи, а не полный безопасный браузер и не готовый весь Dennett host. Host проверяет version/capabilities, resource origin, allowed tools и policy. Отсутствующая функция объявляется unsupported; обычный tool result показывается отдельно, когда предоставлен.

### 5.2. A2UI

Готовый renderer отображает только известные версии и зарегистрированные компоненты. Новый JSON-компонент сам не устанавливает native code. Обновления surface/data model стримятся с сохранением user input. Для сложной custom графики применяется свободный Web Surface или поддержанный embedded app, не обязательное расширение каталога.

Сочетание A2UI/MCP Apps допускается там, где поддержано выбранными реализациями; не требуется проводить каждый ответ через оба. Описанные Google композиции — основание использовать готовые пути, не доказательство совместимости любой версии [AR18].

### 5.3. AG-UI

AG-UI используется как адаптер событий/shared state там, где он нужен подключаемому runtime/frontend. Он не становится новым agent loop, canonical Task store или обязательной третьей ступенью рендера [AR19]. Если нативного канала достаточно, лишний AG-UI-слой не добавляется.

Его snapshots/deltas обновляют нужное presentation state. Команда изменить задачу преобразуется в уже существующую прикладную операцию; клиент не поддерживает самостоятельный «настоящий план AG-UI» наряду с планом/поручением Dennett.

## 6. Выделение, действия и совместное редактирование

Локальные pan/zoom/scroll/сортировка уже полученных данных выполняются без модельного вызова. Контекстное выделение может передаваться для следующего вопроса. Явное «объясни/пересчитай/примени» вызывает сообщение или разрешённый tool. Сам факт интерактивной панели не означает, что агент видит весь DOM и движения мыши.

Interaction record указывает surface instance, artifact/data version, адресат разговора, тип выбора и достаточный payload. При отправке вопроса выбор фиксируется вместе с сообщением; последующий клик его не подменяет. Сброс выбора убирает его из следующего контекста. При нескольких панелях/устройствах неоднозначность не разрешается скрытым смешиванием данных.

Native bridge/AppBridge сообщает только реально доступный выбор. Для простого изображения можно передать выделенную область/снимок, но не выдумывать координаты строк исходной таблицы. Отметка «контекст передан» — доставка, не доказательство понимания модели.

Редактируемый source и версии используют существующий Artifact lifecycle. Agent update имеет base revision и не перезаписывает несохранённую правку пользователя. Несовместимый patch отклоняется/сохраняется отдельным вариантом для согласования. Промежуточная генерация не обозначается окончательным результатом. Создание временной панели не требует постоянной записи каждого hover в Memory.

Закрытие панели не отменяет поручение и не удаляет исходник. При восстановлении используется сохранённая версия или явно обновлённая; mount/render не повторяет send/publish. Статический экспорт не называется полноценным автономным приложением, если у него остались внешние зависимости.

## 7. Изоляция веб-представлений

Недоверенные HTML/JS и сторонние приложения не исполняются в привилегированном Tauri origin с произвольным IPC. Sandbox, CSP/network allowlist, отдельные session/origin boundaries и host capabilities применяются средствами платформы. `iframe` или корректный JSON сами по себе не являются полной защитой.

Сообщения bridge привязаны к созданной хостом сессии и разрешённым операциям; wildcard postMessage/origin без проверки не даёт доверие. Все методы проверяют аргументы, источник и актуальную версию. Секреты, вся память и raw provider credentials не передаются в frontend shared state. Имена файлов/URL проверяются; скачивание не исполняет файл автоматически.

Сеть, файлы, буфер обмена, инструменты, захват микрофона/экрана и открытие внешнего приложения имеют раздельные разрешения. Tool, скрытый от модели, не скрыт от контроля доступа. Синтетическое событие JavaScript не считается явным подтверждением владельца; consequential approval принадлежит доверенной оболочке, отдельно от panel content.

Stop/Emergency остаётся снаружи панели. Crash/loop/перегрузка одной surface допускает её остановку без уничтожения чата и сохранённого артефакта. Fallback не отключает sandbox: неподдержанный web mode показывается файлом/изображением/внешним просмотром с объяснением потерь.

## 8. IPC, схемы и актуальность состояния

Сохраняется generated contract-first направление. Protobuf/schema — описание транспортной границы, не требование структуры рассуждения агента. Внутренние Rust вызовы не превращаются в сеть. Native provider protocol остаётся своим адаптером.

Для M01-сущностей сохраняется смысл ADR-006: аутентифицированный peer/session/epoch, typed result-or-error, admission отдельно от completion, snapshot+deltas и resync при несовместимости. Этот документационный коммит не заменяет сгенерированный wire-код новой эпохой и не разрешает ломать его без отдельной migration. Будущие Memory/UI/replication contracts добавляются их владельцами без speculative placeholders.

Watch получает согласованный cursor по 81. В UI применяются только ожидаемые revisions; старый ответ не откатывает новый state. Connection loss показывает stale/pending; backpressure объединяет token deltas и допускает потерю только объявленного диагностического шума. Control/effect events не теряются как визуальные обновления.

Auth proof и signing keys остаются в native bridge/daemon, не в React renderer. Новый канал/peer повторяет handshake; deep link не переносит готовое разрешение. Большие объекты скачиваются отдельно по scoped handle с проверкой hash, размера и политики.

## 9. Пакеты и запуск процессов

Сборка предоставляет независимые targets Head, Node, memoryd, CLI и UI. **memoryd устанавливается и запускается отдельно от Head**, включая документацию самостоятельного подключения. Для его сборки/тестов не нужны desktop/mobile или главный агент; shared crates ограничены общими контрактами и нужными adapters.

Пакет персонального ПК содержит/подключает PostgreSQL, отдельный memoryd, Head/Node и UI, но не ставит все Python/Node/ML-зависимости заранее. Конкретный provider host устанавливается по необходимости. Один PostgreSQL cluster может обслуживать control/memory раздельными ролями. Standalone Memory package не разворачивает фиктивную агентную ОС.

Windows background runtime и interactive capture helper имеют явные user/session boundaries. macOS использует штатный launch agent/permissions, Linux — подходящий service manager. UI может диагностировать/управлять сервисом, но его завершение не является shutdown всего узла. Для full standby на Windows проверяется жизненный цикл выбранного Linux PostgreSQL окружения, а не только способность открыть окно.

Первый запуск делает local health/identity/storage check, подключает выбранный runtime и выполняет безопасный turn. Нельзя показывать готовый standby или рабочую интеграцию только по наличию бинарника. Отсутствующие credentials и возможности остаются явными.

## 10. Полный резерв, переключение и эксплуатация

Установщик полного резерва готовит тот же совместимый Head, отдельный memoryd, PostgreSQL standby, object/file replication и scopes keys/connections. Readiness из 81 виден в UI: database lag, отсутствие объектов, несовместимая версия, недоступный provider и недостаток диска различаются. Не устанавливается автоматическая власть из наличия реплики.

Управляемый перенос следует 80. Автоматический профиль включается только с испытанным готовым election/fencing механизмом. Без него при partition остаётся локальный ограниченный режим, а не два writable Head. Подготовленная SQL-копия read-only до promotion; локальные drafts не пропадают из-за этого ограничения.

Backup использует pgBackRest и restic по 81. Проверяется полный RecoveryCut, не только число snapshot jobs. Начальные цели: DB recovery point до пяти минут при исправном архивировании; полный cut до шести часов по выбранной политике; более частая защита существенных результатов опциональна. Это не обещание реальных SLO до измерения на установке.

Restore выполняется в изолированную среду: проверить base/WAL/objects/keys/schema; применить deletion/revocation; запустить отдельный memoryd и Head без реальных внешних dispatch; открыть контрольные материалы и проиграть fake Run; лишь после проверки разрешить live connections. Старые queued commands не воспроизводятся как новые.

## 11. Обновления, миграции и конфигурация

Один release manifest описывает версии бинарников, контрактов, схем, расширений PostgreSQL и необходимую совместимость. Он не превращает каждое обновление провайдера в обновление всего приложения. Миграции принадлежат своим доменам, резерв получает данные через WAL. Нельзя применить миграцию SQLite-кэша как серверную migration или наоборот.

Перед разрушительным изменением нужен проверенный recovery path и достаточно staging space. Старый binary не запускается на неподдержанной новой схеме ради обещанного rollback; допустим forward-fix либо restore в новую среду. Mixed-version окно и downgrade failures проверяются. Signature/hash подтверждают источник/целостность, но не семантическую корректность релиза.

Configuration precedence: installation/user/device/project/session overrides в допустимых пределах; effective value и происхождение показываются. Неверная конфигурация не заменяет последнюю валидную. Agent-generated config proposal проходит необходимые проверки и права; не может отключить собственные критерии оценки/Stop. Native model options сохраняются, если не конфликтуют с обязательными ограничениями.

Supply-chain baseline: закреплённые зависимости и внешние actions; минимальные CI permissions; секреты вне публичных fixtures/PR; подписанные release artifacts, checksums и provenance по доступным средствам. Дополнительный TUF/WASM/observability backend не вводится только ради полного списка технологий.

## 12. Observability, ресурсы и приватность

Корреляционные ids связывают команду, сессию, запуск, tool, effect, memory operation и artifact. OpenTelemetry/export adapters могут использоваться без vendor lock-in. Канонический audit/receipt не существует только в отбрасываемом telemetry backend. По умолчанию содержимое памяти, секреты и скрытые рассуждения в логи не пишутся.

Metrics: useful first output, write/replica/index lag, outbox backlog, UNKNOWN/retry, usage по проекту/операции, native runtime health, voice interruption, capture loss, free disk и complete recovery cuts. Внешние provider usage estimates отличаются от точного счётчика.

Цели latency/памяти/диска — versioned budgets с конкретным hardware profile, не произвольные обещания. Stop и локальное сохранение не ждут LLM. Долгая модель не держит DB-lock. Battery/low-bandwidth modes ограничивают фоновую нагрузку и raw media, но не удаляют неподтверждённый capture. Тесты включают pressure/soak, а не только среднюю задержку.

## 13. Архитектура тестирования

**Документы:** актуальность владельцев, ссылки и отсутствие действующих отвергнутых правил; контроль, что архив не стал заданием реализации. Проверка текста не доказывает корректность runtime.

**Domain tests:** grants/revocation, current-state/history, ревизии, idempotency, state transitions, budgets и deletion. Fake clock и стабильные fixtures; нет оплачиваемой модели в каждом unit test.

**Настоящий PostgreSQL:** delayed lower commit/cursor; два workers одного ordering key; crashed lease; snapshot/subscribe race; schema constraints; effect admission/idempotency; migration и restore. Клиентская SQLite проверяется отдельно для drafts/capture/outbox и process death; полного server parity matrix PostgreSQL↔SQLite больше нет.

**Standalone Memory:** сборка без Head/UI; запуск с собственным auth и model/index config; запись, актуализация, поиск, источник, экспорт, удаление, restart; Head отсутствует весь тест. Head отдельно проверяется при падении memoryd и накоплении безопасного outbox.

**Native runtimes:** версии CLI/SDK, permissions/hook coverage, работа собственной памяти, ровно один native executor, cancellation/steer, большие streams, auth/quota errors и recovery. Fake не заменяет хотя бы ограниченный real-provider canary перед заявлением поддержки.

**Реплика и recovery:** base backup, WAL lag/read-only, bytes lag, slot pressure, revoke, плановый перенос, потеря primary, partition двух живых узлов, неподдержанная платформа, rewind/reseed и восстановление около границы retention. Live dispatch блокируется в restore drill.

**Клиенты:** key/focus/a11y, stale state, lossless drafts, notification idempotency, native biometric, voice playback commitment, Windows interactive capture и мобильные ограничения. Browser preview не заменяет native OS проверки.

**Представление L:** PNG без UI-протоколов; custom HTML без установки плагина; selection snapshot; отсутствие семантического канала; user edits при streaming; MCP/A2UI fallback; две панели/два устройства; запрет credential/IPC escape; crash одной surface; reopen без повторного эффекта.

**E01–E10:** реальные старый/новый варианты, одинаковая начальная память/файлы, независимые mutable outputs, unseen cases, лимит бюджета и защищённая процедура принятия. Shared immutable fixtures разрешены; утечка результатов/тестов между попытками — ошибка.

Deterministic simulation и существующий testkit переиспользуются. Небольшой сценарный формат допустим как удобная оболочка; новый универсальный язык workflow/рассуждений не создаётся. Недетерминированные provider tests отделены от deterministic failures. Повторный успешный запуск не скрывает первый fail; flaky tests имеют причину, владельца и срок, critical сценарии не игнорируются.

## 14. Структура реализации и последовательность

Сохраняются понятные roots `services/head`, `services/node`, `services/memoryd`, `apps/desktop`, `apps/mobile`, `adapters`, `crates`, `protocols`, `tests`, `ops`. Каталог не является приказом создать пустой модуль на каждое название. Точные существующие vs будущие места описывает [CODE_MAP](CODE_MAP.md).

Первый сквозной путь связывает UI/CLI → Session/Agent Dennett → готовый runtime → ограниченный результат → separate memoryd → visible state. Функциональность добавляется целостными сценариями, а не сначала всеми пустыми services и manifests.

Архитектурные приоритеты реализации: независимая память и сохранение сессии; одна реальная нативная интеграция с проверенными правами; долговременные ожидания/UNKNOWN; полноценные data replication+recovery; UI L и device continuity; затем увеличение coverage и оптимизация. Это зависимость возможностей, не окончательный план работ агентной команды.

Окончательные правила разработки, распределение агентов, размер этапов и форма владельческой приёмки рассматриваются следующим отдельным этапом. Старые WP/Autonomous Batches не являются автоматическим разрешением продолжить написание приложения. Этот коммит меняет документы, не схемы/протоколы/код работающей реализации.

## 15. Критерии завершения архитектурной редакции

Должны совпадать четыре view: процессы/authority 80, данные/транзакции 81, нативное исполнение 82 и клиенты/эксплуатация 83. Для значимого требования есть владелец, маршрут, отказ и будущая проверка. Неразрешённая техническая неопределённость не обозначается реализованной гарантией.

Точный compatibility profile PostgreSQL на целевых машинах, конкретные версии runtime/UI SDK и фактическое поведение native hooks проверяются реализационными canaries. Их failure имеет fallback или отключение соответствующего mode, а не скрытую зависимость, требующую менять идентичность агента, память и продуктовую логику.

[ARCHITECTURE_VALIDATION.md](ARCHITECTURE_VALIDATION.md) содержит трассировку согласованных изменений, проверенные сценарии на уровне проекта и ограничения данного прохода. Документальная согласованность не равна доказательству абсолютной безошибочности или готовности релиза.
