Версия 2.1 · 2026-09-27 · согласованная архитектурная база, не описание уже реализованных адаптеров.
Применяются F01–F10, E01–E10, L и [M: Claude-first, Codex позже](../specifications/contracts/M_Runtime_Rollout_Contract.md). [80](80_Dennett_System_Architecture_and_Runtime_Topology.md) владеет процессами, [81](81_Dennett_Data_Memory_Storage_Sync_and_Protocol_Architecture.md) — хранением, [83](83_Dennett_Client_Operations_Testing_and_Implementation_Blueprint.md) — представлением и испытаниями. Прежний том 82 целиком заменён; [архив](../archive/architecture-2026-07-13/README.md) не задаёт дополнительные обязанности.

## 1. Два слоя, а не два агентных цикла

**Прикладной слой Dennett сохраняется.** Он связывает агента, сессию, память, рабочую область, разрешения, бюджеты и значимые поручения. Готовый harness даёт модели агентный цикл, встроенные инструменты, контекстные возможности, нативное делегирование и управление сессиями. Подключение Claude SDK/CLI не означает прямую кнопку из UI к модели в обход Dennett.

```text
UI / голос / событие
→ прикладной слой Dennett: выбрать существующего агента и сессию
→ передать нужные инструкции, память и допустимые возможности
→ адаптер готового runtime
→ нативный агентный цикл
→ наблюдаемый результат / инструменты Dennett / обновление состояния
```

Этот слой не является обязательным LLM-посредником, переписывающим каждый запрос. Смысловой план, число помощников, необходимое рассуждение и реакция на новые требования по умолчанию принадлежат агенту. Программа не заставляет его выдавать `NextStep JSON`, обязательный договор перед каждой подзадачей или граф всех отношений.

Собственный универсальный agent loop исключён из обязательного baseline. Для local/других моделей сначала используется подходящий готовый runtime. Короткая собственная реализация допустима только под конкретный обнаруженный пробел с проверками, не как заранее построенная вторая платформа.

## 2. Логические сущности

**Agent** — стабильный участник с id, конфигурацией, доступной памятью и обязанностями. «Главный», «служебный», «рабочий», «временный» — пояснения назначения, не обязательные enum-поля/подклассы. Настройка назначения главного агента ссылается на обычный Agent id. Один агент может работать с несколькими поручениями; завершение одного не удаляет остальные.

**Agent configuration version** содержит инструкции, model/runtime preferences, reasoning settings, skills/tools, memory scope и разрешённые resource limits. Обновление версии не создаёт нового Agent. Полномочия выдаёт владелец/Trust; строка конфигурации не выдаёт их сама.

**Project/Workspace** — область работы и привязанные файлы, а не обязательная оболочка любого короткого поручения. **Session** — разговор и его сохраняемый контекст. **Task/Work** — значимое сохраняемое обязательство, когда нужен его lifecycle. **Run/Attempt** — конкретное исполнение. Простые вопросы остаются в Session без избыточной Task.

**RuntimeBinding** фиксирует adapter, connection, provider session handle, model/options, environment и версии. Provider thread не является Agent id или единственной Task. Нативные временные subagents отображаются по реально доступным событиям; регистрация каждого как отдельного долговременного участника не обязательна. Это не иной класс агента.

**Checkpoint** хранит явную цель, сообщения/ссылки на контекст, материал результата, workspace version, неопределённые действия, настройки runtime и доступный continuation handle. Скрытые рассуждения не являются условием восстановления.

## 3. Общая граница готового runtime

`AgentRuntimePort` имеет операции describe/probe, start/resume, send/steer, cancel, snapshot, close и поток видимых событий. Неподдержанная функция возвращает explicit unsupported; адаптер не симулирует гарантированную приостановку или перенос скрытого состояния.

Descriptor сообщает версии, способы авторизации, работу с инструментами и согласованиями, modes continuation, observable events, cancellation, используемые ресурсы и доступные native extensions. Это технический handshake адаптера, не JSON-анкета смыслового поручения.

Нормализуются admission, visible text/media, tool/effect observations, artifacts, usage, warning/error, completion и session state. Исходные разрешённые native данные можно сохранить отдельным versioned opaque payload/артефактом. Они не принимаются core policy как новое право и не копируются всем агентам. Private reasoning не публикуется и не используется как доверенный интерфейс системы.

Нормализация не выполняет инструмент повторно. Опубликованное событие `tool_started` — наблюдение, не предварительное разрешение. Недостаточная наблюдаемость показывается как ограничение, а не заполняется придуманным trace.

## 4. Codex: прямой адаптер процесса, не обход Dennett

**Отложено: R-CODEX.** Описание сохраняется для будущего подключения; до отдельного решения владельца не реализовывать и не включать в зависимости, первый запуск или приёмку D0–D9. Первым реализуется §5. Перед активацией заново проверить актуальный протокол и условия поставщика.

Рекомендуемый глубокий путь: Rust-адаптер Dennett управляет локальным `codex app-server` через документированный двусторонний протокол процесса. Отдельный Node.js-пересыльщик не требуется, когда не добавляет полезных функций. При необходимости полноценного SDK его host остаётся допустимым; обязанности управления lifecycle и восстановления не удаляются [AR01], [AR02].

Версия бинарника закрепляется; генерируемые схемы берутся из той же версии. Инициализация, thread/turn operations, продолжение, steer/interrupt, запросы разрешений и события сверяются с этим bundle. Новый неизвестный event не даёт право выполнить действие; несовместимая обязательная функция отключает соответствующий mode с объяснением.

Базовый транспорт — локальный stdio с ограниченными буферами, раздельными stdout protocol/stderr logs, контролем жизненного цикла и сохранением session id. Прямой удалённый listener не выставляется в сеть по умолчанию. Официальная документация на дату проверки отмечает экспериментальность App Server/части transport-функций: это открытая зависимость интеграционного испытания, не обещание production-поддержки поставщиком. Есть возможность использовать другой поддержанный SDK/runtime-адаптер в том же порту без изменения Agent/Memory модели.

**Нативные tools исполняет Codex.** На запрос разрешения адаптер отвечает решением в доступном scope; затем native runtime выполняет либо отклоняет команду. Dennett не запускает её ещё раз. File/diff/test результат сверяется с реальной средой.

Инструменты Dennett доступны через MCP/CLI и, когда выбранная версия подтверждает достаточную поддержку, через native dynamic tool bridge. Экспериментальный dynamic-tool интерфейс не является единственным путём к памяти. Workspace, effective instructions и инструменты memoryd предоставляются через согласованное окружение; прямой доступ к SQL/секретам не выдаётся.

## 5. Claude Code и Claude Agent SDK

**D0 проверяет, D1 реализует Claude Code как первый runtime; Codex не является зависимостью этого пути.** Под «Claude Code» здесь понимается готовый агентный цикл и инструменты Anthropic, а не только модель через Messages API и не внешность терминала. Порядок выпуска определён [контрактом M](../specifications/contracts/M_Runtime_Rollout_Contract.md); конкретная модель и effort остаются настройками.

### 5.1. Официальные способы подключения

Для встроенного многотурового чата рекомендуемый исходный вариант — официальный **Claude Agent SDK**, TypeScript-host с `@anthropic-ai/claude-agent-sdk` вне Rust Head. Он сохраняет готовый цикл Claude Code и даёт callbacks, поток событий, пользовательский ввод и управление сессией. Это полезный SDK-host, не пустой пересыльщик; создавать рядом собственный tool loop не нужно. Python-host допустим, если конкретная интеграция оправдывает его; две реализации SDK-host заранее не требуются [CR01], [CR02].

Официальный неизменённый **Claude Code CLI** остаётся отдельным поддерживаемым путём, в том числе для пользовательского штатного входа. Rust-адаптер может запускать документированный машинный режим процесса без SDK, когда этот режим действительно покрывает выбранные операции. Не парсить ANSI/экран терминала и не опираться на недокументированный внутренний control protocol. CLI и SDK — интерфейсы к готовому движку, не разные классы агентов. Для интерактивного пути нельзя подменить callbacks и продолжение набором несвязанных `claude -p` с одной строкой; D0 проверяет точные режимы [CR01], [CR02], [CR03].

В начале фиксируются версия runtime/SDK, выбранный способ входа, реально доступные streaming input, approvals, вопрос пользователю, interrupt, resume, tools и subagents. Если CLI не покрывает обязательную возможность, используется поддержанный SDK-путь в разрешённом способе авторизации либо предъявляется конкретный блокер. Нельзя автоматически включить платный API, Codex или bypass permissions для получения зелёной демонстрации. Отсутствие разрешённого входа не меняет выбранного первого поставщика.

### 5.2. Сессии и поток управления

Для SDK используется streaming input, а не только поток текста на выходе. Прикладной слой принимает уточнения, разрешает вопросы/approvals и обрабатывает interrupt во время работы. SDK имеет single-message и streaming modes с разными возможностями; проверяется нужный режим, не только слово «streaming» [CR02].

Сохраняется привязка Dennett Agent/Session к конкретному Claude `session_id`, рабочей области и профилю. Возобновление использует явный ID: выбор «последнего разговора в папке» недопустим при нескольких сессиях. Fork создаёт отдельное native continuation, но не копирует автоматически файлы, права и каноническую Memory. Один native session не получает одновременно двух управляющих writers. Наличие ID само по себе не гарантирует продолжение на другом узле: нужны доступные transcript/state и рабочие файлы; иначе применяется честный rehydrate по §11 [CR04].

Принимаются наблюдаемые сообщения, tool events, запрошенные решения, итоговый result, ошибки и доступная usage. Окончание текста не равно завершению инструмента; error-result и исключение/exit status не игнорируются. Интерфейс не получает скрытые рассуждения как обязательный канал. Экспериментальный TypeScript V2 session API, удалённый из актуальной SDK-линии, не используется как основа; выбранная стабильная поверхность перепроверяется при закреплении версии [CR04].

### 5.3. Инструкции, нативные настройки и память

System prompt задаётся явно. Для сопровождаемой человеком работы с кодом допустим `claude_code` preset с необходимым append. Для главного оркестратора и не-кодирующих агентов — соответствующий их назначению собственный prompt, сохраняющий нужные инструкции инструментов и границы доступа. Нельзя считать, что пустой `systemPrompt` SDK автоматически равен полному CLI-профилю. Не навязывать всем агентам терминальную роль программиста [CR05].

Источники настроек выбираются осознанно и отражаются в diagnostic snapshot: проектные CLAUDE.md/`.claude`, пользовательские настройки, skills, plugins и MCP не подхватываются из чужого профиля молча. Загрузка контекста не означает разрешение запускать произвольный project hook или сервер. До запуска непроверенного проекта определяется доверенная конфигурация; импортируемые executable hooks/plugins проверяются как capabilities, а не просто текст памяти. `settingSources` и другие параметры сверяются с закреплённой версией, без предположения о вечном default. Пустой список `settingSources` сам по себе не отключает все глобальные источники, auto-memory или managed policy; нужен проверенный профиль и изоляция, не обход обязательной политики организации [CR05], [CR06].

`--bare` не является безусловным ускорением: в документированном CLI он отключает автозагрузку значительной части контекста и не использует подписочный OAuth. Его можно применять в подходящем API/проверочном профиле с явной передачей необходимых средств, но нельзя сломать им пользовательский вход или незаметно убрать память/skills. Обычный headless CLI также не показывает интерактивную проверку доверия папке, поэтому выбор окружения выполняется до него [CR03].

Память Dennett остаётся самостоятельным `memoryd`. Начальные инструкции/выбранный контекст передаются на вход; последующий поиск, чтение источника и запись вызываются через scoped MCP-инструменты или CLI Dennett. Встроенный custom tool SDK является фасадом той же операции, не второй памятью внутри host. Native auto-memory и session transcript не становятся единственным источником истины; их включение, область и удаление явно согласуются с Memory Fabric [CR07].

### 5.4. Инструменты, вопросы и разрешения

Встроенные инструменты выполняет Claude runtime; инструмент Dennett — владелец операции Head/Node/memoryd. Hook или событие разрешения не запускают вторую копию действия. Identity/scope проверяются на стороне операции, а не по имени агента в prompt. MCP server и native Bash не получают прямой доступ к PostgreSQL или общей коллекции секретов.

`canUseTool` обслуживает запросы решения, но не видит автоматически все уже разрешённые вызовы. `allowedTools` — правила автоматического разрешения, а не полное ограничение каталога. Если нужна обязательная предисполнительная проверка конкретной границы, используется документированный `PreToolUse` и внешние ограничения среды; hooks не считаются песочницей и не требуют дополнительной LLM на каждый вызов. Обход через Bash/network/подагента проверяется отдельно [CR08], [CR09].

`AskUserQuestion`, запрос разрешения инструмента и согласование результата представлены отдельно. Ответ владельца возвращается исходному ожидающему запросу в той же сессии/попытке; позднее подтверждение не разрешает изменившиеся параметры. Нет ответа или callback недоступен — ожидание/отказ по политике, не автоматическое согласие. Голос и UI используют эти же операции. Разрешённые операции должны оставаться работоспособными [CR10].

### 5.5. Помощники, завершение и ресурсы

Нативные subagents, skills, plugins и раскрытие подходящих инструментов используются в поддерживаемых версиях без собственного диспетчера каждого reasoning step. Область инструментов и памяти проверяется для помощника так же, как для родителя. Не предполагать, что обычный subagent получает весь родительский разговор: native fork и отдельное prompt-поручение различаются. Все помощники входят в бюджет поручения; SDK-состав возможностей проверяется отдельно от интерактивных Claude Code agent teams [CR06], [CR11].

Локальный процессный supervisor принадлежит Dennett Node, не UI. Сначала запрашивается поддержанный interrupt и сохраняются частичный результат и открытые эффекты; аварийное завершение имеет отдельный статус. Head сохраняет долговременные таймеры и обязательства: фоновые задачи CLI имеют собственный lifecycle и не объявляются автоматически бессрочными задачами Dennett. Идентичный session resume не отменяет уже совершённый эффект. Native file checkpoint также не является rollback базы/памяти/публикации [CR03], [CR12].

Модель/effort и доступные лимиты задаются выбранным профилем. Нельзя копировать названия reasoning-уровней Codex в Claude без проверки поддерживаемых параметров. Usage учитывается по фактическим доступным событиям без повторного суммирования одного итога; отсутствие сведений обозначается неизвестностью. Исчерпание лимита и login expiry показываются пользователю, не лечатся незаявленной платной маршрутизацией.

### 5.6. Авторизация и публичное описание

SDK-интеграция стороннего продукта использует разрешённую API/cloud-provider авторизацию либо предварительное разрешение Anthropic на иной способ. Пользовательский вход в неизменённый официальный Claude Code проходит штатный поток Anthropic; действуют отдельные условия размещения бинарника. Не собирать/копировать подписочные токены, не подменять клиент, не перепродавать чужой usage и не объявлять временный доступ к подписочному лимиту бессрочным правом продукта. При failover доступ на новом узле проверяется, а не создаётся копированием личных credentials [CR01], [CR13], [CR14].

SDK-backed агент в интерфейсе называется «Claude Agent»/«Claude» в контексте агентов или собственным именем Dennett; он не выдаётся за официальный продукт «Claude Code». Для действительно запущенного официального бинарника допустимо точно указать этот факт без присвоения бренда. Условия и стоимость маршрута видны до подключения. Это техническая граница интеграции на дату проверки, не юридическая гарантия для любой схемы распространения [CR01], [CR13].

Claude-first не заменяет voice ASR/TTS/realtime другими неподтверждёнными возможностями SDK и не меняет независимость Memory. Все обязательные функции D0–D9 реализуются по своим контрактам; Codex остаётся будущим дополнительным исполнителем.

## 6. Остальные providers и локальные модели

OpenAI Agents SDK/API, Google ADK, OpenHands и будущие движки остаются сменными адаптерами, а не отдельными источниками канонической истины. Их полезные native возможности можно раскрывать в настройках; общий порт не обязан обрезать всё до минимума одного поставщика.

Local model server — capability: проверяются artifact/revision/hash, license, custom code trust, quantization, RAM/VRAM, modalities, tool/context support и load/unload. OpenAI-compatible endpoint не объявляется полностью семантически совместимым. Тяжёлые модели не живут внутри Head/memoryd. Сервисы inference могут совместно использоваться по ресурсной политике без смешивания пользовательских контекстов.

Для direct chat выбранная пользователем модель сохраняется. Внутреннее разрешённое routing может менять модель/effort/число помощников по задаче и ходу работы. Не вводится обязательный LLM-router или классификатор сложности. Registry даёт реальные доступные возможности и сведения о quota/health; agent выбирает содержательную стратегию. Смена модели сама не создаёт нового агента.

## 7. Один набор функций Dennett: CLI, MCP, API и UI

Прикладные операции принадлежат домену: память — memoryd; поручения/агенты/расписания/effects — Head; локальные файлы/процессы — Node. CLI, MCP и интерфейс клиента — тонкие фасады этих же операций. Не создаются отдельные реализации памяти для каждого способа вызова.

Примеры назначения CLI (не утверждение о готовых командах): поиск/открытие памяти, получение артефакта, отправка сообщения агенту, просмотр/остановка конкретного запуска. Интерфейс поддерживает `--help`, ограниченный текстовый результат, стабильные exit codes и необязательный machine-readable output для интеграций. Большой текст передаётся stdin/file reference, не требованием поместить всю задачу в shell argument.

Agent пользуется свободным текстом. Имя, project id или флаг `--agent` являются селекторами, не доказательством личности; исполняющий daemon проверяет peer/scoped session credential. CLI запускается аргументами без shell-интерполяции непроверенных строк, с ограниченным окружением. Секреты не попадают в командную строку, help, логи и output. Административные команды доступны только при отдельном праве.

MCP-фасад раскрывает релевантные группы инструментов по мере необходимости; тысячи схем не загружаются в каждый prompt. При отсутствии shell применяется MCP/native tool bridge. При недоступности MCP CLI не обходит отсутствующее разрешение. Memory CLI/MCP может обращаться прямо к standalone memoryd, не создавая Head.

## 8. Кто исполняет действие и кто его разрешает

**Native operation:** ready-made runtime исполняет собственный tool в предоставленной среде. Dennett связывает policy/approval hook, sandbox и credentials с действующими правами, получает фактические события/результат. Нет повторного исполнения в Tool Broker.

**Dennett operation:** runtime вызывает наш tool; доменный обработчик проверяет доступ, выполняет действие и возвращает результат. Для внешних эффектов применяется единый lifecycle 81 и бизнес-контракт B/D.

**Внешний агент/A2A:** получает текстовое ограниченное поручение и возвращает наблюдаемый результат; удалённый статус не создаёт локальное право или завершение автоматически. Его ограничения переносимости и cancel показываются явно.

Политика обеспечивается там, где эффект действительно возможен. Если нативный shell имеет unrestricted сеть и сырые credentials, нельзя обещать, что ограничение только нашего почтового инструмента запретит отправку этим shell. Для точной гарантии используются подходящие credentials/network/sandbox controls либо операция переводится на поддержанный brokered путь. Нет обязательного security-agent на каждый шаг, но журнал постфактум не выдаётся за reference monitor.

## 9. Контекст и доступ к Memory Fabric

Сохраняются два пути: нужный исходный контекст при начале/продолжении работы и обращение агента к Memory API во время работы. Передавать весь архив на каждый turn не требуется. Context Manifest — техническая запись разрешённых источников/версий, а не готовый system prompt и не обязательная форма ответа модели.

Context service соединяет актуальную цель, сообщения, effective instructions, текущие project files/branch, ссылки на выбранную память, capabilities и ограничения. Для изменчивого состояния читается соответствующий живой владелец, не только старая заметка. Memory результат сохраняет происхождение, актуальность и uncertainty.

Native instruction semantics сохраняются: AGENTS.md, CLAUDE.md/rules и навыки применяются с их областью/приоритетом. Дополнительная инструкция по возможности добавляется без разрушения системного поведения harness. Дублирующая загрузка одного правила через workspace и manual prompt устраняется. Внешние документы и советы памяти не получают системного авторитета.

Compaction использует готовые средства, когда они достаточны; важные решения/ссылки/незавершённые действия остаются восстанавливаемыми в Dennett. Summary не становится фактом памяти без обычного write path. При невозможности точного native context audit показываются известные источники и ограничение, а не выдуманный «полный контекст».

Автономные memory writes проходят ту же историю/дедупликацию/current-state обработку. Рабочие notes остаются редактируемым текстом. Нативная память провайдера может быть вспомогательной, но не единственной копией критического решения; её синхронизация не создаёт конкурирующего canonical store.

## 10. Поручение, помощь, уточнение и завершение

Агент делегирует обычным текстом через нативные средства или общий messaging tool. Техническая адресация хранит, куда доставлено сообщение, но не компилирует договорённость в граф consumers/depends_on. Переиспользуемый способ сотрудничества — skill/instruction, а не обязательная жёсткая схема процесса.

Ответственность, переписка и использование части результата различаются в тексте. При отмене агент читает договорённости и уточняет у исполнителей, что больше не нужно. Общая работа для других поручений не уничтожается вслепую. Программа исполняет адресованную остановку; нативное дерево subprocess/cancellation token управляет ресурсами конкретного исполнения, не подменяет эту смысловую координацию.

Уточнение пользователя передаётся нативным steer/queue/interrupt+continue в доступном режиме. Отдельного алгоритма определения затронутых частей плана нет. Явный запрет нового внешнего действия изменяет соответствующую разрешённую операцию/мандат, а не остаётся только фразой в одном чате. Уже отправленное действие не отменяется редактированием сообщения.

Результат имеет outcome succeeded/partial/failed/cancelled/no_op, текст, артефакты/changes, проверенные evidence, нерешённые пункты и сведения о последствиях. Это прикладная запись результата; свободный ответ агента не обязан быть огромным JSON. Нативное completion — сигнал о завершении исполнения, не доказательство достижения всех требований. Проверки соответствуют задаче; дополнительный reviewer не обязателен для каждого turn.

## 11. Ожидание, продолжение и отмена

Срок жизни сессии и агентного процесса не определяет срок обязательства. Нативный durable механизм используется, если реально переживает нужный restart; иначе Head хранит ожидание/таймер и позже продолжает тот же логический Work через runtime adapter. Два активных планировщика одной и той же обязанности не создаются.

Уровни продолжения: native resume; поддержанный snapshot; rehydrate из явной истории/материалов; свежий старт с потерей native continuity, видимой пользователю. Cross-provider перенос не обещает перенос скрытого состояния.

Cancel сначала ограничивает новые запрещённые последствия, затем прерывает подходящие native/provider/tool операции, сохраняет partial result и состояние начатых эффектов. Если остановка внешнего исполнителя не подтверждена, статус остаётся stopping/unknown, а не «всё завершено». Устаревший callback не может изменить новое исполнение после смены authority/attempt, но полезный поздний результат можно сохранить и оценить отдельно.

Смысловую реакцию на timeout/ошибку выбирает агент. Инфраструктура гарантирует доставку известного факта и сохранность принятого состояния, не прописывает отдельный промпт-сценарий восстановления для каждого случая.

## 12. Capabilities, плагины и подключение новых средств

Registry сохраняет раздельно discovery/possession/trust/activation/ownership/health/utility. Установка не означает разрешение; пользовательский ручной выбор не проходит обязательный конкурс полезности. Автоматически найденная возможность остаётся кандидатом до допустимого принятия. Skills, плагины, models, MCP и connectors используют общие lifecycle-принципы, но имеют различный тип исполнения.

Descriptor содержит version/fingerprint, host needs, config schema, scopes, native extensions и compatibility. Иная Python/Node среда изолируется через host только при необходимости; не каждый adapter получает процесс. Несовместимые или по-разному доверенные компоненты с секретами не объединяются в один host ради числа процессов.

Update/fork/ownership и полезная delta навыка не смешиваются: внешний пакет не переписывается без соответствующего владельца; локальный fork хранит provenance. Обновление permissions/auth scope требует актуального разрешения. Отключение capabilities не удаляет созданные ими пользовательские артефакты.

MCP resources/prompts/tools/apps, sampling/elicitation и обратные вызовы проходят собственные права и budgets. Resource text не становится permission. Внешний запрос модели не получает API-key; inference выполняется через допустимый connection. UI contribution подчиняется L и клиентской изоляции, а не протокольной популярности.

## 13. Переписка, публикация и computer-use

Connector устанавливает точный account/thread/recipient, загружает свежий контекст, предлагает/подготавливает разрешённое содержание и отдельно выполняет dispatch. Операции send/publish/delete используют сохранённые parameters, разрешение, idempotency и receipt. Timeout после dispatch означает UNKNOWN до проверки, а не автоматическую повторную отправку. Фоновый retry имеет общий budget и не обнуляет счётчик при смене процесса.

Computer-use сначала использует достаточный API/DOM/accessibility path, при необходимости pixels. Backend выбирается по реальным возможностям и trust. Takeover/Stop не зависит от модели. Клик по Send не является успехом без доступного наблюдения среды; неизвестный исход не воспроизводится слепо через другой backend.

Подтверждённый эффект не становится обычным undo при восстановлении worktree/сессии. Review approval, permission approval и публикация — разные операции с разными владельцами.

## 14. Голос: быстрый путь и обдумывание

Voice Session владеет разговором, turn revisions, выбранным собеседником и слышимым выводом; media-кодеки и устройства работают в подходящем локальном/специализированном процессе. Head координирует, но не сериализует каждый аудиофрейм в PostgreSQL.

Поддержаны realtime/cascade/hybrid adapters. Локально работают допустимые VAD, pre-roll, wake, mute и barge-in; тяжёлое размышление может быть поручено другому агенту/модели, не блокируя простые голосовые функции. Дополнительный voice-sidecar не обязателен на каждый turn.

Partial ASR — не committed command. В контекст услышанного попадает действительно воспроизведённая часть TTS. При прерывании прекращается playback, сохраняется начало речи пользователя, поздний старый audio не воспроизводится. «Угу» и содержательное прерывание различаются Voice policy, а не одним универсальным stop.

Голос передаёт поручение существующему агенту, не создавая другого участника только из-за модальности. Вопрос о выделении получает зафиксированный UI-context по L. Важное подтверждение идёт через доверенный интерфейс; голосовое сходство не выдаёт права. Одна активная conversational ownership на сессию исключает одновременное скрытое воспроизведение несколькими устройствами.

Meeting/ambient различают чужую речь, личные заметки, shared output и команды. Capture consent/privacy policies применяются до облачной передачи. Стриминг и handoff показывают поддержанные возможности конкретной платформы, не обещают вечный мобильный background runtime.

## 15. Сенсорные источники

Audio: OS permission → локальный ring buffer/VAD/echo checks → дешёвый отбор → discard/wake/commit candidate → разрешённая транскрипция/память. Сырой поток не сохраняется навсегда автоматически; явное «запомни последнее» использует доступный pre-roll в пределах политики.

Screen: события приложения/окна и доступные DOM/accessibility/selection → change detection → нужный screenshot/keyframe → privacy/redaction → dedupe/temporal context → staged evidence. OCR — fallback, не обязательный повтор структурированного чтения. Одинаковые pixels не приводят к вызову тяжёлой модели на каждом таймере.

Native/Screenpipe и другие capture adapters остаются сменными. Отключение ОС, занятость микрофона и запрет окна отображаются честно. На диске/сети действуют bounds из 80/81; отсутствие места не оправдывает молчаливую потерю явно сохранённой записи.

## 16. Реальная проверка самоулучшений

По E01–E10 интеллектуальные части — диагноз, критика, предложения и новые тестовые случаи — выполняются агентами. Программная Evaluation application обеспечивает версии, подготовку эквивалентных исходных состояний, фактические запуски, наблюдаемые результаты/стоимость и допустимое применение. Это модуль существующего orchestration/testkit, не постоянная команда надсмотрщиков и не новая обязательная production-служба.

Каждая попытка получает отдельный workspace и memory-write область/изолированную копию memoryd данных; общий immutable source разрешён read-only при одинаковом начальном доступе. Один вариант не читает outputs, новые notes и provider session другого. Environment реагирует на реальные действия, а не возвращает записанный ответ чужому запросу.

Сравниваются исходный провал, прежние успешные случаи и неиспользованные для настройки ситуации; учитываются итог, нарушения, полезность действий, затраты и задержка. Большее число tools/agents само по себе не штраф. Независимость судей не выдумывается по количеству копий модели. Внешний реальный send не выполняется в replay-песочнице.

Budget включает диагностику, кандидатов, обе попытки, судей и повторы. Недостаток данных не означает победу новой версии. Автор кандидата не меняет критерии/пороги в том же сравнении; изменение прав и способа приёмки не принимается как обычная prompt-оптимизация. Продвижение scoped, обратимое и наблюдаемое; rollback не отменяет уже случившееся внешнее действие. Поведение памяти сравнивается при разработке, без нового обязательного предархитектурного этапа.

## 17. Контроль интеграции

Для каждого runtime adapter, реально входящего в текущий выпуск, проверяются: старт/continue, память во время работы, native tool исполняется один раз, Dennett tool достигает своего домена, точный permission boundary, user steer/cancel, повтор/late event, восстановление после crash, quota/login expiry, версия протокола, расходы и отсутствие утечки секретов.

Для первого Claude-пути применяются [C01–C12](../testing/CLAUDE_RUNTIME_ACCEPTANCE.md). Codex-canary отложен вместе с R-CODEX, но не помечен пройденным. Нужны real-provider canaries отдельно от deterministic fakes. Успех фиктивного адаптера не доказывает поддержку callback выбранным CLI. [83](83_Dennett_Client_Operations_Testing_and_Implementation_Blueprint.md) определяет поставку и тестовые границы; [матрица](ARCHITECTURE_VALIDATION.md) фиксирует непроверенные на runtime предпосылки.
