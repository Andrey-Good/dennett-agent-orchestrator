## 1. Роли хранилищ

**PostgreSQL — единственная каноническая серверная реализация** для локального Head, выделенного сервера и полного резерва. Стандартный cluster содержит логические базы `dennett_control` и `dennett_memory` с разными ролями, миграциями и владельцами. Отдельные database names не означают два обязательных PostgreSQL-процесса. Standalone memoryd использует только memory-домен.

SQLite/нативное embedded-хранилище клиента содержит кэш разрешённых проекций, черновики, staged captures, локальную очередь и операции для последующего согласования. В нём **не реализуется вторая полная серверная Memory Fabric**. Оно не является заменой PostgreSQL standby. Серверные migrations не обязаны иметь SQLite-эквивалент; переносимые клиентские операции имеют единые семантические проверки.

Большие bytes находятся в immutable content-addressed Object Store; стандартный backend — обычные файлы, S3-compatible backend подключаемый. Проекты остаются обычными папками/Git-репозиториями. Секреты — в keystore/vault; SQL содержит необходимые ссылки и зашифрованные дескрипторы, не открытый набор токенов. Поисковые индексы производны.

Нельзя синхронизировать живые SQLite/PG-файлы общим file-sync. Нельзя реплицировать все серверные таблицы в клиентские SQLite как обход обработки офлайн-команд. Штатная физическая репликация PostgreSQL применяется **к полным совместимым резервным узлам**, а не к телефонам и любым клиентам [AR04], [AR08].

## 2. Идентичность, время и версии

Стабильные идентификаторы — UUID с типом/областью объекта. Их лексикографический порядок и время создания не используются как порядок commit. Идентичность агента не включает модель, prompt hash или reasoning effort; это версии конфигурации.

Каждая изменяемая каноническая запись имеет revision; запрос изменения может предъявлять ожидаемую revision. Содержимое версии артефакта/источника неизменно, текущий указатель меняется транзакционно. Оригинальная история, актуальная проекция и поисковый индекс различаются.

Для памяти сохраняются время события, наблюдения, поступления и применимости; отсутствие известного времени не заменяется выдуманной точностью. Порядок device операций основан на `(device_id, device_epoch, source_sequence)`, не только на часах. Для расписаний сохраняются IANA timezone и выбранный смысл wall-time/instant; DST и путешествия следуют бизнес-контракту I.

Ссылка на источник включает стабильную версию и нужный anchor: строки, страницу, диапазон времени, область изображения, DOM/Git-фрагмент. Она не превращает внешнее содержимое в инструкцию или разрешение.

## 3. Канонические семейства данных

### 3.1. Control

Хранятся агенты и версии их конфигураций; проекты и привязки путей; сессии/сообщения; значимые поручения и попытки исполнения; RuntimeBinding и непрозрачные provider handles; checkpoints; ожидания/расписания; Inbox и решения; grants/revocations; effect claims/attempts/receipts; capabilities/connections и usage; артефакты/версии/публикации; миграции/backup records; durable outbox и принятые команды.

Простое сообщение не требует отдельной Task. Нативные subagents можно отображать по реально доступным сведениям, но из их lineage не строится управляющий граф смысловых зависимостей Dennett. Текстовые договорённости хранятся в сообщениях/заметках/поручениях. Связь результата с поручением, receipt с действием и event с источником — учёт данных, не автоматическая топология кооперации.

### 3.2. Memory

Семантика [Memory Fabric 10](../specifications/10_Dennett_Memory_Fabric.md) сохраняется, включая:

- `memory_events` и `evidence_objects`: оригиналы, происхождение, наблюдаемое время, lifecycle и область;
- `observations`, `episodes`, `claims`, `claim_evidence`: открытое содержание, поддержка/опровержение и история;
- `current_state_items`, `conflicts`, `corrections`: актуальная версия, разногласия и основания изменения;
- `topic_documents`, `topic_document_versions`, `human_notes`: человекочитаемые рабочие документы и история редактирования;
- `relations`, `causal_traces`: связи фактов и происхождения, а не граф управления агентами;
- `prospective_intents`, `procedures`: намерения/опыт в памяти; исполнение расписания не дублируется в Memory;
- `instruction_sources` и версии эффективного набора, project packs, retention/deletion obligations, index generations и processing jobs.

Свободный текст и расширяемые facets не заменяются обязательной онтологией. Наличие семейства в архитектуре не означает, что все сложные обработчики обязаны работать в первом выпуске; конфигурации сравниваются во время разработки. Это не разрешение удалить историю, актуальность, дедупликацию или provenance из требований.

### 3.3. Исправленная идентичность evidence-связи

Вместо nullable `ordinal` в первичном ключе используется отдельный стабильный `link_id`:

```sql
CREATE TABLE event_evidence_links (
    link_id UUID PRIMARY KEY,
    event_id UUID NOT NULL REFERENCES memory_events(event_id),
    evidence_id UUID NOT NULL REFERENCES evidence_objects(evidence_id),
    relationship TEXT NOT NULL,
    anchor JSONB NULL,
    ordinal INTEGER NULL CHECK (ordinal IS NULL OR ordinal >= 0),
    revision BIGINT NOT NULL DEFAULT 1 CHECK (revision > 0)
);
CREATE INDEX event_evidence_by_event
    ON event_evidence_links(event_id, evidence_id, relationship);
```

Это целевая форма, не уже применённая миграция. Порядковый номер не определяет идентичность: изменение порядка не создаёт новую связь. Повтор той же принятой операции использует тот же link_id; request id и fingerprint позволяют отличить повтор от противоречащего payload. Разные anchors одного источника могут иметь разные link_id; нельзя запрещать их общей уникальностью только по паре event/evidence. История существенных исправлений сохраняется Memory events. Обязательное поле первичного ключа не объявляется nullable [AR09].

## 4. Приём и актуализация памяти

Источник фиксируется раньше успешности смысловой обработки. Для крупных данных: получить bytes в staging, проверить размер/тип/hash/политику, надёжно разместить immutable object, затем одной memory-транзакцией записать событие, ссылки и outbox обработки. Малый inline payload допустим только в заданном лимите.

Далее обработчики memoryd выполняют разрешённые дедупликацию, admission, извлечение полезного смысла, обновление рабочих документов/current state и индексов. Дубликат bytes не означает дубликат события: одинаковый экран или цитата в другой момент могут иметь самостоятельное значение. Шум не обязан становиться долговременным Claim. Отказ обработчика не уничтожает принятый источник; retry привязан к версии обработчика и операции.

Актуальный документ даёт лучший известный ответ с датой и основанием, а не уничтожает прежнюю истину. Поздняя информация разрешается по применимости и provenance, не по одному времени загрузки. Human-owned текст не перезаписывается генератором без принятой политики; конфликт сохраняется, когда однозначного решения нет.

Операции записи, исправления, forgetting и экспорта доступны через Memory API standalone. Изменяемая операция проверяет текущий режим primary/read-only, область доступа и revision. Нельзя полагаться только на доверие к вызвавшему Head.

## 5. Чтение, контекст и индексы

Базовые серверные средства — PostgreSQL structured/temporal lookup, FTS и pgvector; отдельные vector/graph/reranker adapters подключаются по пользе. Их выбор не меняет canonical store. Предварительные ограничения scope/permission применяются до раскрытия текста, facets и связанных объектов; финальная проверка доступа остаётся обязательной.

Memory API поддерживает обычные текстовые запросы и открытие стабильного handle, чтение текущего состояния либо состояния на указанное время, ссылки на оригиналы, ограничения размера ответа и явные partial/freshness признаки. Результат поиска — не разрешение совершить действие. Свежие данные дополняют отстающий индекс через recent overlay.

Каждое поколение индекса имеет source watermark, модель/версию, chunker/builder, применённые corrections/deletions и статус. Построение нового поколения: snapshot → догнать события → проверить → атомарно переключить active pointer. Старое поколение сохраняется только на разрешённый срок; rollback не возвращает забытые данные. Повреждённый индекс отключается, источники и запись памяти остаются доступны. Запрос не называется полным, если часть источников не индексирована.

На клиентах exact/FTS по разрешённому кэшу и необязательный локальный поиск обслуживают offline-чтение. Полный резервный memoryd может читать standby с указанием подтверждённой позиции; это не гарантирует актуальность после отрыва от primary [AR08]. Standby-чтение не обновляет серверные usage/audit/index/job tables: такие локальные наблюдения временно фиксируются вне read-only replica и при необходимости передаются владельцу. Долгое чтение может быть отменено WAL replay; клиент получает повторяемую ошибку, не ложное повреждение памяти.

## 6. Memory API и независимость сервиса

Версионируемый интерфейс memoryd предоставляет health/capabilities; ingest/append; search/open; notes/current/history; correction; delete/forget status; export/import; processing/index status и управляемые rebuild операции. CLI/MCP/HTTP являются фасадами этих же обработчиков; внутренний transport — из 80. Большие объекты передаются handles/stream, а не гигантской строкой в каждом сообщении.

В интегрированном режиме memoryd проверяет scoped credential доверенного issuer и собственную область данных. В standalone-режиме тот же verifier interface использует локально настроенную identity/policy. Главный агент не создаётся ради работы памяти. Модельные и индексные зависимости подключаются к узким портам, могут использовать свои разрешённые connections и не читают control tables.

Изоляция БД и object namespace позволяет отдельно тестировать, переносить, обновлять и использовать память. Memoryd имеет собственную очередь обработки и обслуживания памяти; её таймеры не требуют Head scheduler. Это локальный lifecycle индексов/дедупликации, не второй глобальный агентный оркестратор. Endpoint под Head не является единственным доступным входом. Корневые ключи или широкие права не выдаются стороннему агенту автоматически.

## 7. Границы атомарности и внешние bytes

Внутри одного домена current state, revision, обязательное событие, idempotency record и outbox фиксируются одной транзакцией. Нет сетевого вызова, обращения к модели или длительного filesystem-copy внутри открытой SQL-транзакции.

Control↔Memory не используют распределённую транзакцию. Control надёжно сохраняет результат и `MemoryCommitRequested`; memoryd идемпотентно принимает его и возвращает ссылку/событие. До этого результат доступен в control/artifact store со статусом ожидающей записи в память. Прямой самостоятельный write в memoryd не требует фиктивной Task в Head.

Object Store использует staged bytes → fsync/проверка доступной гарантии backend → immutable placement → SQL reference. Незавершённый staging можно убрать после срока; orphan после сбоя metadata восстанавливается или собирается GC. Удаление общих bytes учитывает всех законных владельцев/retention roots, а не только исчезновение одной ссылки.

CAS identity scoped по установке/области шифрования: одинаковый hash не даёт возможности проверить существование чужого private object. Hash проверяет целостность, не доверие к содержимому. Ключи, шифрование транспорта и разрешения проверяются отдельно.

Изменение обычных project files: работать в разрешённом workspace/worktree, применить изменение, наблюдать реальные bytes/commit, записать результат. При сбое metadata watcher/reconciliation восстанавливает факт; БД не объявляет несуществующий файл записанным. Внешнее редактирование не становится транзакцией PostgreSQL.

## 8. Outbox: порядок без пропущенных фиксаций

### 8.1. Идентификатор не является курсором

UUID, BIGSERIAL, wall clock и произвольный `MAX(id)` не используются как доказательство порядка commit. Номер мог быть выделен до задержавшейся транзакции и появиться позже уже прочитанного номера [AR10].

Для канонического потока хранится `stream_counters(stream_id, committed_seq)`. Изменяющая транзакция блокирует нужный counter, увеличивает его обычным transactional UPDATE, записывает изменение состояния и stream event и завершает commit, удерживая блокировку только на короткой секции фиксации. Rollback откатывает counter вместе с событием. Следующая запись этого потока получает номер после предыдущего commit, а не до него. Нельзя заменить эту операцию вызовом PostgreSQL sequence.

Control имеет собственный system stream для согласованных UI transitions; memory — собственные потоки областей и изменений. Глобальная нумерация всего аудио, всех токенов и всех устройств не требуется. При нескольких counters используется стабильный порядок блокировки. Идентификатор курсора включает installation/authority epoch, stream_id и confirmed position; курсоры разных потоков не сравниваются как одно число.

### 8.2. Параллельная доставка

Outbox содержит event_id, stream position, payload schema, destination/consumer, available_at, attempt count, lease owner/generation/deadline и last_error. Для событий с порядком есть ordering_key и последовательность этого ключа.

`SKIP LOCKED` используется только вместе с условием доступности **самого раннего ещё не подтверждённого события ключа**. Занятый ранний элемент не позволяет выбрать следующий того же ключа. Разные ключи обрабатываются параллельно [AR11].

Захват выполняется короткой транзакцией; отправка — вне неё. Новый владелец получает новую lease generation, устаревший не может подтвердить работу за нового. Сетевой повтор всё равно возможен: потребитель идемпотентно фиксирует событие и собственный эффект одной своей транзакцией, либо использует отдельный lifecycle внешнего действия. Это at-least-once delivery с контролем повторов, не универсальная exactly-once сеть.

Потребитель не применяет следующий обязательный переход объекта, пока отсутствует предыдущий; дубликат распознаётся. Сбойный элемент паркует только свой ключ и создаёт наблюдаемую проблему; перепрыгнуть через него и продолжить как будто всё обработано нельзя. Независимый event не нуждается в ненужном порядке.

### 8.3. Снимок плюс изменения

Снимок состояния и confirmed cursor читаются в одном согласованном MVCC snapshot владельца потока. Далее клиент получает все изменения после него. Между получением снимка и подпиской события удерживаются или доступны для catch-up. При истёкшем retention, разрыве последовательности, неизвестной schema/epoch клиент останавливает применение и запрашивает новый снимок.

Фильтр доступа не раскрывает чужое содержимое. Продвижение через скрытые записи подтверждает сервер как корректно просканированный диапазон; отсутствие payload у клиента не трактуется как потерянное разрешённое событие. При отзыве доступа кэш очищается в принятой области; курсор не разрешает читать отозванные данные.

Снимки разных доменов имеют вектор курсоров и могут быть частичными; не обещается единая междоменная SQL-транзакция. UI не превращает временный lag Memory в завершённый memory commit.

## 9. Клиентские операции и локальная полезность

Device operation сначала сохраняется локально с постоянным operation_id, source sequence, областью, ожидаемой revision, временем и ссылками на staged bytes. При reconnect она предъявляется действующему владельцу для проверки identity/epoch, доступа, актуальности, idempotency и наличия данных.

Возможные исходы: принято, отклонено, конфликт, устарело, требуется действие владельца. Новое разрешение или внешняя отправка не выполняются из старой offline-очереди без актуальной проверки. Одинаковый operation_id с другим содержимым — ошибка, не разрешённая перезапись.

Пока PostgreSQL ПК является standby, локальные изменения не пишутся в неё. Черновики, captures и разрешённые локальные project changes остаются отдельными staged операциями. После безопасного получения роли Head они проходят тот же приём; не применяется SQL-merge двух primary.

Конфликт notes сохраняет base и обе версии; агент может предложить слияние текстом. Permissions/effects/head authority не используют last-write-wins. Git/file sync не заменяет domain sync. Готовый read-sync adapter допустим только при сохранении этих границ.

## 10. Полная реплика PostgreSQL и готовность резерва

Для полного standby используются base backup и native WAL streaming, а не реконструкция control/memory через клиентские CRUD-запросы. Реплицируется канонический cluster, включая оба домена; standby read-only до продвижения. Major version, бинарная архитектура, extensions и пути совместимы по 80; extension binaries и конфигурация ОС устанавливаются отдельно [AR04], [AR08].

Асинхронность — обычный профиль: явно измеряется sent/write/flush/replay lag и известный диапазон потери. Строгий профиль ждёт durable acknowledgement выбранного synchronous standby; недоступность всех требуемых подтверждающих узлов задерживает защищённую запись. Недоступный телефон не обязан блокировать весь сервер. Ослабление гарантии не происходит молча. Тайм-аут ожидания подтверждения не доказывает rollback уже committed транзакции; результат проверяется по operation_id.

SQL-реплика не переносит object files, Git/worktrees, веса моделей, running processes, логины провайдеров и OS-keystore автоматически. Для них существует `ReplicaReadiness`: совместимый runtime, позиции БД, манифест полученных канонических объектов и project snapshots, доступ к необходимым ключам и connections, проверка свободных ресурсов. Состояния: preparing, catching_up, ready_for_cut, degraded, stale, revoked. Это операционное состояние копии, не граф взаимозависимости агентов.

Полная копия может защищать все канонические данные установки, но «полностью готова» относится к конкретному проверенному срезу. Если база догнала, а bytes ещё нет, операция чтения показывает недоступность; promotion не объявляет все функции восстановленными. Записи, для которых требуется защищённое подтверждение и на резерве, размещают необходимые immutable bytes там до обещания такого уровня защиты.

Replication slots/WAL retention ограничены по размеру и сроку простоя. Превышение приводит к явному stale/reseed, не к бесконечному росту диска primary [AR07]. Реплика не заменяет исторический backup: ошибочное удаление тоже передаётся.

## 11. RecoveryCut: согласованный восстановимый набор

`RecoveryCut` описывает PostgreSQL system identifier/timeline и restore point/LSN, позиции control/memory streams, версии schemas/runtime, immutable object manifest, project snapshot manifests, references на защищённые конфигурации и ключи, полноту и результат проверки. Текущая строка «backup successful» не заменяет этот набор.

Для baseline полного среза:

1. Проверить место/доступ и временно закрыть приём новых канонических записей в участвующих Head и memoryd через ограниченный maintenance barrier. Standalone-вход memoryd тоже соблюдает barrier; он не зависит от несуществующей Task.
2. Закончить короткие SQL commits и зарегистрировать stable file/object snapshots. Не ждать завершения всех мыслительных задач: их checkpoints и неизвестные эффекты фиксируются.
3. Защитить manifest roots от GC; зафиксировать cut marker в участвующих доменах. После этого создать именованную restore point PostgreSQL отдельным разрешённым backup/replication компонентом.
4. Сохранить sealed manifest с позицией restore point, затем снять barrier. Файлы копируются по immutable manifests уже без длительной остановки записи.
5. Объявить cut защищённым только после проверки нужных WAL, backup base, объектов и ключевых предпосылок в целевом месте. Неудачный/частичный cut остаётся неполным, previous healthy cut сохраняется.

Это короткий координируемый барьер, не distributed SQL transaction и не вечная блокировка при модели. У него есть deadline и идемпотентная отмена: частично полученный barrier не объявляет cut полным; crash coordinator освобождает остановку управляемо без открытия записи во время незавершённой фиксации. При standalone-memory срез охватывает только memory-domain и его объекты. Именованная restore point создаётся с отдельным ограниченным backup credential; model/ordinary agent не получает PostgreSQL superuser [AR20]. Project snapshot не выдаётся за атомарный снимок произвольно редактируемой внешней папки: применяется поддержанный filesystem snapshot либо проверенный набор неизменяемых версий/commit+dirty data. Если обязательный snapshot стабилизировать не удалось, cut не считается полным.

Для восстановления используется допустимый cut либо более поздняя DB-точка только при доказанной доступности всех нужных объектов/версий. Наличие свежего WAL без файлов не даёт полной системной PITR-гарантии.

## 12. Backup, retention и удаление

Сохраняются pgBackRest для PostgreSQL и restic для immutable objects/config/project snapshots. Baseline DB-PITR окно — 30 дней при реально сохранённой цепочке. Пример направления настройки: `repo1-retention-full-type=time`, `repo1-retention-full=30`; WAL не истекает раньше необходимой retained base. Требование «ровно две последние недельные цепочки» удалено как несовместимое с этим окном [AR12].

Частота: continuous WAL; weekly full и incremental/differential по объёму; согласованный полный RecoveryCut целевой частоты до 6 часов и перед существенной миграцией. Это начальные эксплуатационные цели, не измеренная гарантия. DB RPO до пяти минут не называется RPO всего набора, если files/cuts отстают на шесть часов. Protected cut после важного результата может создаваться чаще. Метрики отдельно показывают latest DB recoverable point, latest complete cut и остаточную потерю по классам данных.

GC не удаляет bytes, необходимые retained cut/версии, только потому что исчез текущий live pointer. Сроки restic и object GC согласованы с полным recovery window. Forgetting/retention policy может ограничить доступ к старому содержимому; residual backup expiry/crypto-erasure показываются честно. Restore сначала применяет актуальные deletion/revocation obligations, иначе старый backup способен воскресить забытое.

Удаление различает перестать использовать, убрать проекцию, удалить оригинал и удалить разрешённые производные/реплики. Идентификаторы и content-free audit могут сохраняться по политике, но не должны содержать удалённый секрет в ошибке/trace. Внешняя публикация имеет отдельный revoke/receipt, её не удаляет исчезновение локального Artifact.

## 13. Миграции, экспорт и смена индекса

Memoryd владеет memory migrations, Head — control migrations; один release coordinator проверяет матрицу совместимости. Expand/backfill/validate/contract предпочтительнее одновременного разрушительного изменения. Долгая backfill не блокирует все пользовательские операции; несовместимый старый клиент получает понятный отказ или read-only.

Standby получает SQL/данные через репликацию, не применяет миграцию второй раз. Upgrade major PostgreSQL — отдельная проверенная миграция с backup/restore планом, не штатное переключение standby другой major версии. pg_rewind используется только при совместимых предпосылках и не для слияния самостоятельных изменений [AR06].

Portable project/memory packs используют versioned manifest, source refs, hashes, разрешённые текстовые документы и объекты. Секреты и личные overlays не включаются без явно выбранного допустимого scope. Импорт сначала staged/проверен; инструкции и исполняемый код не активируются из-за корректного hash. Полная миграция установки отличается от обмена проектным пакетом.

## 14. Наблюдаемость и проверка данных

Нужны метрики lag streams/indexes/replicas, размер outbox/WAL/object staging, parked keys, conflicts, rejected stale commands, retry/unknown effects, completeness cuts и deletion lag. Корреляционные IDs не раскрывают скрытые рассуждения и private payload.

Тесты охватывают: delayed commit меньшего номера; SKIP LOCKED с двумя workers одного ключа; crash до/после send/ack; повтор старого lease; snapshot/subscribe race; gap/retention/epoch change; nullable ordinal; один source с несколькими anchors; direct standalone memory writes; PG standby read-only; offline drafts; base snapshot+WAL catch-up; missing object; revoked key; old-primary return; boundary-day backup restore; forgotten data after restore.

Проверка invariants и примеров схемы не означает, что migrations всего приложения уже выполнены. [Отчёт соответствия](ARCHITECTURE_VALIDATION.md) фиксирует границы реально сделанного.
